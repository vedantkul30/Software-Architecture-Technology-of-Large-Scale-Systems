Replication for Horizontal Scalability

Web, Service & Database Layers

Syllabus scope: Replication → Stateful Web Replication → Stateless Web Replication → Stateless Service Replication → Database Replication → Database Replication Types.

Assumed baseline: Performance module (latency, caching fundamentals), Vertical vs Horizontal scaling, Reverse proxy, Scalability principles.

Deferred to later lectures (not deep-dived here): Cache-pattern taxonomy (cache-aside/write-through — see "Caching for scalability"), Database partitioning/sharding, Load balancer internals, Async/message-driven scalability, Microservices vertical partitioning.

1. Core Concept & Intuition

One-Sentence Definition

Replication is the practice of running multiple identical copies of a system component (web tier, service tier, or database) so that load, and optionally data, is distributed across them — trading off a spectrum of consistency, complexity, and cost for horizontal scalability and availability.

Why This Concept Exists

Before replication, a system's only lever for handling more load was vertical scaling — bigger CPU, more RAM, faster disk on a single machine. That lever has a hard ceiling: hardware has physical and economic limits, and a single machine is a single point of failure (SPOF). The industry needed a way to scale that (a) has no theoretical ceiling and (b) survives the loss of any one node. The answer was to stop relying on one instance and instead run N instances of the same component, splitting traffic among them. But the moment you have N instances instead of one, a new question appears: does each instance need to remember anything about the client between requests? That single question is what splits replication into stateful and stateless flavors, and it is the organizing idea of this entire lecture block.

Architecture Analogy

Think of a bank branch chain. A single branch (one instance) can only serve so many customers per hour before the queue backs up — that's vertical scaling maxing out. So the bank opens three branches (replication). Now: does a customer have to return to the exact same branch because their file is sitting in a drawer there (stateful — like a session pinned to Node 1)? Or does every branch have equal access to a central records vault (the database) or a shared drive-through folder cabinet (shared cache), so a customer can walk into any branch and be served identically (stateless)? The stateful branch is faster for repeat visits (the teller already has your folder on the desk) but breaks badly if that specific branch burns down — your open transaction data is gone. The stateless branches are slightly slower per visit (someone has to walk to the vault) but any branch survives the loss of any other.

How a Real System Sees It

Inside a production request:

  • A Load Balancer sits in front of N web-tier instances and picks one to route to (round-robin, least-connections, or — in stateful architectures — sticky sessions keyed by a cookie).
  • The chosen web instance either serves from local memory (stateful) or hits a shared cache (Redis/Memcached) or goes straight to the service layer.
  • The service layer, itself replicated statelessly, does business logic and talks to the database.
  • The database layer is where real state lives permanently, and its replication topology (master-slave or master-master) determines the consistency and availability guarantees of the entire system above it.

2. Transcript Content — The "What"

2.1 Replication, defined

Replication = running multiple instances of the same component. Two flavors:

  • Stateless replication: only code is replicated. No component-local data outlives a single request; any data generated is transient and scoped to that request.
  • Stateful replication: both code and data are replicated/maintained per instance. State (e.g., a session) persists across requests on a specific instance.

Layer-by-layer defaults from the transcript:

Layer Typical choice Why
Web tier Stateless preferred; stateful only for extreme low-latency needs Simpler, more scalable, more reliable
Service tier Stateless (near-always) Same reasoning as web tier; little motivation for stateful services
Database tier Inherently stateful The database is the durable state — replication here is about durability & read-scaling, not a stateless/stateful choice

2.2 Stateful Replication in the Web Layer

Problem it solves: Without any local caching, every request for e.g. a user profile requires: Client → Web instance → Service → Database → Service → Web instance → Client. Multiple network hops = high latency.

Mechanism:

  1. First request for user 101 arrives at, say, Node 1 (arbitrarily chosen by the load balancer).
  2. Node 1 fetches the profile from Service → Database, and before responding, stores the profile in a local in-memory session keyed by a session ID (e.g., 101).
  3. The response to the client includes a cookie carrying two pieces of information: the session ID (101) and the node identity (Node 1).
  4. On subsequent requests, the load balancer reads the cookie and routes the client back to Node 1 specifically — this routing mechanism is called a sticky session.
  5. Node 1 serves the request directly from memory — no service/database hop needed.

ASCII flow:

First request:
Client → LB → Node1(web) → Service → DB
                 ↑ stores session{id:101, data:profile} in memory
Client ← LB ← Node1 [Set-Cookie: session=101, node=1]

Subsequent requests:
Client [Cookie: session=101, node=1] → LB (reads cookie) → Node1 (routes here only)
Client ← Node1 (served directly from memory, no Service/DB hop)

Two serious limitations (explicit in transcript):

a) Scalability limitation — memory-bound connection ceiling.
Each session occupies a fixed chunk of memory (e.g., 1 MB). If a machine has 500 MB available for sessions, it can hold at most 500 concurrent sessions — even if its CPU/thread capacity could otherwise serve 2,000 simultaneous connections. To serve 2,000 clients you'd now need 4 machines instead of 1, purely because of the session-memory ceiling, not actual compute capacity. This directly inflates infrastructure cost.

b) Reliability limitation — node failure = data loss + latency spike.
If Node 1 goes down:

  • The load balancer must reroute the client to Node 2 or Node 3, neither of which has the cached profile.
  • That node must fall back to the full Service → Database path → latency spike for all users whose sessions lived on Node 1, until their data is re-cached.
  • Worse: if the user had made unsaved changes to session data that were never propagated to the database, those changes are permanently lost when Node 1 dies. The user sees stale/old data on their next request.

Mitigation mentioned: Application servers like WebLogic or WebSphere offer clustered sessions — session data is replicated to other nodes as changes happen, so a node failure can fail over to a node with a session copy. But this adds significant operational and execution complexity, and is explicitly called "a messy affair to handle" — not the preferred general approach.

Explicit guidance: Go stateful only when latency requirements are extremely critical and outweigh the scalability/reliability costs.

2.3 Stateless Replication in the Web Layer

Mechanism: No session data lives in web-instance memory at all. Every request — 1st, 2nd, or Nth — goes through the same path if data isn't cached elsewhere.

Solving the resulting latency problem — two caching layers, not local memory:

  1. Shared server-side cache (Redis / Memcached): First request populates the cache after fetching from Service→DB. Subsequent requests — routed to any instance, no stickiness required — check the shared cache first. Cache hit avoids the DB round-trip. Slightly slower than local-memory (stateful) access, but far faster than hitting DB every time.
  2. Client-side cache (cookies): Small, user-specific data can be stored directly in the client's cookie and sent with every request, eliminating server-side lookups entirely for that data. Limited by cookie size constraints and added network cost per request — only viable for small, per-user data, not large or shared data.

ASCII flow:

Request → LB → any Node (no stickiness needed)
                  ↓ check shared cache (Redis/Memcached)
             hit? → serve from cache
             miss? → Service → DB → populate cache → serve

Why this is preferred:

  • Scalability: No per-node memory ceiling tied to session count; any instance can serve any client.
  • Reliability: If a web node dies, others continue serving unaffected — no data loss, since state lives in the shared cache/DB, not node memory. If the shared cache itself dies, nodes simply fall back to DB and repopulate the cache once it's back — graceful degradation, not data loss.

Explicit rule of thumb from the instructor: Default to stateless replication. Use stateful web replication only when latency requirements are extremely critical.

2.4 Stateless Replication of Services

The service tier follows the same reasoning as the web tier — stateless is the default, with a shared cache available for frequently-read, rarely-modified data.

New nuance introduced here — the shared-resource/locking problem:
When a component was a single instance, concurrent threads on that one machine could synchronize using OS- or language-level locking primitives (mutexes, monitors, etc.) to safely coordinate access to a shared resource (e.g., a shared file).

Once that component is replicated across N separate instances/processes, in-process/OS-level locking no longer works — each instance has its own memory space and its own OS-level lock table; they can't see each other's locks.

Solution pattern (explicit in transcript): Move the lock into a common external resource — typically a lock table in the database. A row is created representing the shared resource (e.g., the file); an instance takes a row-level lock (e.g., via a transaction), performs the modification, and commits — releasing the lock for the next instance to acquire.

Instance A                  DB (lock table)              Instance B
   |-- BEGIN, lock row F ------>|                             |
   |   (modify shared file)     |                              |
   |-- COMMIT (release lock) -->|                              |
                                 |<---- BEGIN, lock row F ------|
                                 |                    (modify)  |
                                 |<---- COMMIT (release) -------|

This is a direct, practical consequence of replication that's easy to overlook: replicating a component can silently break existing concurrency-control assumptions, and you must re-architect synchronization around a shared, externally visible resource.

2.5 Database Replication — Overview

Unlike the web/service tiers, the database is inherently stateful — replication here is about durability, read-scalability, and availability, not a stateless/stateless choice.

Two things replication achieves at the DB layer:

  1. Read replicas for high read scalability — offload read traffic from the primary so it can focus on writes (and remaining reads).
  2. Backup replicas for high availability — if the primary (master) dies, a backup can be promoted to become the new master, preserving write availability.

Typical real-world topology (explicit in transcript): One master + several asynchronous read replicas (for scale) + one synchronous backup replica (for zero-data-loss failover).

2.6 Database Replication Types — Master-Slave vs Master-Master

Master-Slave (Primary-Secondary)

  • Writes: only to master. Reads: master or any slave/secondary.
  • Replication is unidirectional: master → slave(s).
  • Two sync modes:
Property Asynchronous Synchronous
Write acknowledged when... committed on master only committed on both master and secondary
Write latency Lower Higher
Consistency Eventually consistent (secondary can lag/serve stale reads) Strongly consistent (always in sync at commit time)
Failure mode if master dies Un-propagated changes are lost when secondary is promoted No data loss on failover
Failure mode if secondary dies Writes continue fine on master (secondary catches up later) Writes become unavailable — master can't complete a transaction that requires secondary ack
Typical use Read replicas (scale reads, tolerate slight staleness) Backup replica (zero data loss, accept write-availability risk)

Practical pattern: several async read replicas (for scale) + one sync backup replica (for safe failover) — this is exactly the topology described in §2.5.

Why master-slave is popular: There is only one source of truth (master) — slaves must simply converge to master's state. This structurally eliminates write conflicts, which is the single biggest reason this configuration dominates in practice.

Master-Master (Peer-to-Peer / No-Master)

  • Reads and writes allowed on either instance.
  • Replication is bidirectional, most commonly asynchronous.
  • Core risk — write conflicts: if the same record is modified on both instances around the same time, reconciliation produces a conflict that must be resolved via explicit business rules (last-write-wins, merge logic, etc.) — non-trivial and error-prone.
  • Secondary risk — transaction ordering: clock skew between instances (which can never be fully eliminated) can cause ambiguity in the order in which concurrent transactions should be reconciled.
  • Why it's used anyway — geo-distributed low-latency writes: if users are split across regions (e.g., North America and AsiaPac), master-slave would force all writes to a single region's master, giving one region great latency and the other region poor latency (extra network hop across continents). Master-master lets each region write to its local instance with low latency, at the cost of needing conflict-resolution logic.
  • Availability: doesn't matter which instance goes down — reads/writes continue on the other. Higher availability than master-slave in that specific sense.

Comparison table:

Dimension Master-Slave Master-Master
Write path Single master only Any instance
Write conflicts Impossible (single source of truth) Possible — must be explicitly resolved
Popularity High (simple, safe) Low (used for specific geo use case)
Best for General-purpose read scaling + backup/HA Globally distributed users needing low-latency local writes
Ordering guarantees Trivial (single writer) Non-trivial (clock skew across peers)

3. Deep Technical Explanation

3.1 Why sticky sessions are structurally fragile

A sticky session couples routing correctness to node liveness. The load balancer's routing decision (via cookie) is a promise that a specific node holds specific data — but that promise has no built-in expiry-on-failure mechanism. When the node dies, the promise silently becomes false, and the system has no way to know what data was lost until a user complains about missing changes. This is a classic implicit coupling failure: two independent concerns (load balancing and data locality) were merged into one mechanism (the cookie), and the failure mode of one now cascades into the other.

3.2 Why "eventually consistent" async replication is not a bug, it's a deliberate trade

Asynchronous master-slave replication commits on the master first, propagates later. During the propagation window, reads from the slave can return stale data. This is not a design flaw — it's the direct, unavoidable consequence of decoupling write-latency from replication-latency. You cannot have (a) low write latency, (b) strong read consistency across replicas, and (c) high write availability during partial failures, simultaneously — this is a concrete instance of trade-offs formalized by the CAP theorem and, for the latency dimension specifically, PACELC (if Partitioned, choose Availability or Consistency; Else, choose Latency or Consistency).

3.3 Why synchronous replication trades availability, not just latency

It's tempting to think synchronous replication is "just slower." In fact it changes an availability property: because commit success requires both nodes to acknowledge, the health of the secondary becomes a hard dependency for every write, not just for reads. A single-node failure (the secondary) now blocks 100% of write traffic even though the master is perfectly healthy. This is the crux of the trade-off described in the transcript, and it's why synchronous mode is reserved narrowly for a backup pair, not fanned out across many read replicas — every synchronous replica you add multiplies the number of independent failure points that can block writes.

3.4 Why replicating a stateless component isn't "free" — the hidden coordination cost

Stateless replication removes session state, but it does not remove shared resource state (files, counters, external systems). The transcript's file-locking example shows the hidden cost: replication converts an intra-process concurrency problem (solvable with cheap in-memory locks) into a distributed concurrency problem (requiring an external, shared arbiter like a DB lock table). This is strictly more expensive: a DB row lock involves a network round trip and transactional overhead, versus a few CPU cycles for an in-memory mutex. Anyone claiming "we went stateless, so we have no consistency problems" is ignoring this class of issue.

3.5 Failure cases and hidden complexity summary

Component Failure scenario Consequence
Stateful web node Node crash Data loss for un-persisted session changes + latency spike for orphaned sessions
Shared cache (Redis/Memcached) Cache node/cluster down Graceful degradation — DB becomes source of truth again, cache warms back up
Async master-slave Master crash before propagation Permanent loss of un-replicated writes
Sync master-slave Secondary crash Write unavailability on an otherwise-healthy master
Master-master Concurrent writes to same record Write conflict requiring resolution logic; possible silent data corruption if rules are incomplete
Replicated service + shared file Concurrent instance writes without DB lock table Race condition / corrupted shared resource

4. Architecture Trade-offs — The "Why"

Stateful vs Stateless Web Replication

Stateful Stateless
Choose when Ultra-low latency is a hard requirement and outweighs cost/risk Default choice for almost everything
Avoid when You need elastic scaling, simple ops, or high reliability Rarely a reason to avoid — nearly always safe default
Problems introduced Memory-bound scaling ceiling, data loss on node failure, sticky-session complexity, clustering complexity if mitigated Slightly higher per-request latency (cache/DB hop)
Alternative designs Clustered sessions (WebLogic/WebSphere), external session store (effectively converts to stateless-with-cache) N/A — this is the alternative
How FAANG-scale systems solve it Almost universally stateless web/service tiers backed by a fast shared cache (Redis clusters) — session affinity is avoided specifically because it breaks elastic autoscaling

Asynchronous vs Synchronous Master-Slave Replication

Asynchronous Synchronous
Choose when Read scaling, low-latency reads/writes acceptable staleness Zero data-loss tolerance for a backup instance
Avoid when You need a guaranteed zero-loss failover target You need many replicas or low write latency at scale
Problems introduced Possible stale reads, possible data loss on master failure Write unavailability if any sync replica is down; higher write latency
Alternative designs Quorum-based replication (write succeeds if majority of replicas ack — used by systems like Cassandra/DynamoDB) softens the all-or-nothing trade-off

Master-Slave vs Master-Master

Master-Slave Master-Master
Choose when Single-region or single-source-of-truth workloads; general purpose Multi-region, latency-sensitive writes with tolerable/resolvable conflicts
Avoid when You need multi-region low-latency writes You can avoid the complexity — conflict resolution is genuinely hard
Problems introduced Cross-region write latency if used globally Write conflicts, clock-skew-driven ordering ambiguity
How FAANG-scale systems solve it Often layer in causal/version-vector conflict resolution (e.g., DynamoDB's vector clocks) or route by geography with per-region "ownership" of record ranges to minimize true multi-writer conflicts

5. Production System Perspective

  • Sticky sessions in practice: Older enterprise Java shops (banking, insurance) historically leaned on stateful sessions with clustered failover (WebLogic/WebSphere) — precisely the pattern the transcript flags as "messy." Most cloud-native companies (Netflix, Uber, Stripe) deliberately architect stateless services and externalize all session/user state to fast stores (Redis, DynamoDB), specifically so that autoscaling and rolling deployments never risk data loss on instance termination.
  • Shared cache at scale: Services like Netflix's EVCache (a Memcached-based layer) exist precisely to give stateless services near-memory-speed access to frequently-read data without paying full database latency — a production embodiment of §2.3's shared-cache pattern.
  • Read replica fan-out: Systems like Instagram (historically Postgres) and many e-commerce platforms run a master plus many async read replicas to absorb read-heavy traffic (product pages, feeds) while keeping writes (checkout, posts) funneled through a single master for consistency.
  • Multi-region writes: Databases explicitly designed around the master-master idea — e.g., Cassandra (leaderless, tunable consistency) and DynamoDB global tables — exist because companies like Amazon needed low-latency local writes in every region while accepting eventual conflict resolution (typically last-writer-wins with vector clocks).

6. System Design Perspective

What this concept affects: Scalability (read/write capacity), Reliability (blast radius of a node failure), Availability (can writes/reads continue during partial failure), Performance (added hops vs added memory access), Operational complexity (clustering, conflict resolution), Cost (extra machines needed purely due to memory-bound session ceilings).

"If I ignored this concept, what would go wrong?"

  • Sticking with a single, unreplicated web/service/DB instance means the system has a hard scalability ceiling (vertical scaling limits) and a single point of failure — any crash takes down the entire system.
  • Choosing stateful web replication by default (without a genuine latency justification) silently creates a cost multiplier (more machines needed for the same load) and a data-loss risk on every node failure — a decision that looks fine in a demo and fails expensively at scale.
  • Choosing synchronous replication everywhere (thinking "consistency is always better") silently creates a write-availability bottleneck tied to the health of every synchronous replica — a subtle failure mode that only shows up under real network partitions.
  • Replicating services without addressing the shared-resource locking problem (§3.4) introduces silent race conditions on shared files/resources that may not surface until concurrent load is high enough to trigger them in production.

7. Performance Analysis

  • Memory: Stateful sessions consume per-instance RAM proportional to concurrent user count — the direct cause of the 500-vs-2000 connection ceiling example. This is a cache-locality benefit (fastest possible access) traded for a hard capacity ceiling.
  • Network latency: Every hop removed (local memory > shared cache > service+DB) is a proportional latency win, but each hop also removes a resilience/scalability constraint — it's a two-axis trade, not a pure win.
  • Write latency (sync vs async): Sync replication directly adds the round-trip time to the secondary onto every write's critical path — this is the classic "extra network hop equals extra tail latency" pattern, and at global scale this round trip can dominate P99 write latency.
  • Throughput implications: Async master-slave decouples write throughput from replica health entirely, maximizing master throughput; sync coupling caps effective throughput at the slower of (master, secondary).
  • Lock contention (§3.4): Moving from in-memory locks to DB row locks introduces real contention costs — every replicated instance now competes for the same row lock, and under high concurrency this can become a serialization bottleneck across the whole fleet, not just within one process.

8. Real-World Architecture Examples

Scenario A — E-commerce product catalog (read-heavy, latency-tolerant):
Problem: Millions of read-heavy product page views vs comparatively few writes (admin updates). Chosen: master + several async read replicas + shared Redis cache in front of the web tier. Trade-off accepted: occasional few-hundred-ms staleness on product data after an update. Alternative: fully synchronous replication (rejected — would tank write throughput for a benefit customers wouldn't notice). Failure scenario: master dies → a synchronous backup (kept separately, not one of the read replicas) is promoted; the read replicas simply re-point to the new master.

Scenario B — Global SaaS collaboration tool (multi-region writes):
Problem: users in the US and EU both need to write low-latency edits to shared documents. Chosen: master-master (or leaderless) replication across regions with operational transformation / CRDT-based conflict resolution. Trade-off accepted: engineering investment in conflict resolution logic. Alternative: single global master (rejected — EU users would suffer transatlantic write latency). Failure scenario: simultaneous edits to the same paragraph from both regions — resolved via CRDT merge rather than last-writer-wins to avoid silently discarding a user's edit.

Scenario C — Session-heavy real-time trading dashboard (extreme low-latency need):
Problem: a trading desk UI needs sub-millisecond access to a user's live position data, and DB/cache round trips are unacceptable. Chosen: deliberately stateful web replication with sticky sessions, accepting reduced elasticity, in one of the rare cases the transcript explicitly allows. Trade-off accepted: reduced max concurrent users per box, and a defined incident runbook for handling node failure (accepting brief data gaps, or layering in clustered session replication despite the complexity cost). Alternative: shared in-memory data grid (e.g., Hazelcast) instead of pure local memory — a middle ground giving near-local speed with better failure tolerance.

10. Interview Questions

Basic

  1. What is the difference between stateful and stateless replication?
    Answer: Stateless replicates only code — no data outlives a single request on a given instance. Stateful replicates code and data — instances hold long-lived, request-independent data (e.g., sessions) locally. Trade-off: stateful gives lower latency for repeat access but couples correctness to a specific node's availability, hurting scalability and reliability.
  2. What is a sticky session, and what problem does it solve?
    Answer: A load-balancer mechanism that routes a client's repeat requests to the same backend node, based on a cookie encoding session ID and node identity. It solves the problem of a stateful node needing to be the one serving a given user's cached data. It introduces fragility: if that node dies, the "stickiness" promise is broken.
  3. What is the difference between master-slave and master-master database replication?
    Answer: Master-slave: writes go only to a single master; slaves are read-only and unidirectionally synced — no write conflicts possible. Master-master: any instance accepts writes; replication is bidirectional — write conflicts are possible and must be resolved.

Intermediate

  1. You need to scale reads on a database that gets 100x more reads than writes. Would you use async or sync master-slave replication, and why?
    Answer: Asynchronous — for read replicas, you want low write latency on the master and are willing to tolerate a small propagation delay (eventual consistency) on reads. Synchronous replication would unnecessarily slow every write and risk write unavailability if any replica has issues — reserved for a small number of backup replicas, not fan-out read replicas.
  2. A stateful web architecture works fine at low traffic but starts requiring far more machines than expected as traffic grows. Why?
    Answer: Session data occupies memory per connection; the machine's true CPU/thread-based capacity (e.g., 2,000 connections) is overridden by a much lower memory-bound ceiling (e.g., 500 sessions at 1MB each on 500MB available). Scaling to the same real user load now requires proportionally more machines than a stateless design would, inflating cost.
  3. Compare synchronous master-slave replication to master-master replication in terms of availability.
    Answer: Synchronous master-slave: doesn't matter which of the two nodes fails, writes become unavailable, because a commit requires both nodes' acknowledgment. Master-master: writes/reads can continue on whichever instance survives — higher raw availability — but at the structural cost of possible write conflicts that synchronous master-slave never has to face.

Advanced

  1. Design the replication topology for a globally distributed social media app where users in the US, EU, and Asia all post content with low latency, and explain the trade-offs.
    Answer: Master-master (or leaderless, e.g., Cassandra-style) replication across three regional clusters, each accepting local writes, with asynchronous bidirectional (or all-to-all) propagation. Trade-offs: must implement conflict resolution (e.g., last-writer-wins with vector clocks, or CRDTs for structured merges), must accept eventual consistency for cross-region reads, and must handle clock-skew-driven ordering ambiguity. Alternative (single global master) would fix consistency and eliminate conflicts, but at the cost of unacceptable write latency for two of the three regions — rejected because the product's core UX (posting) is latency-sensitive.
  2. Explain, in CAP/PACELC terms, why asynchronous master-slave replication cannot give you both low write latency and strong read consistency simultaneously.
    Answer: Asynchronous replication decouples the write-commit event from replica propagation to minimize write latency (only the master needs to ack). That decoupling is exactly what creates the window where a replica read can be stale — you've explicitly chosen Latency over Consistency (the "ELC" in PACELC) during normal operation, and Availability over Consistency ("AC") during a partition, because you don't want writes blocked waiting on a replica.
  3. A team replicated a previously single-instance service that periodically writes an aggregate counter to a shared file. After replication, they see corrupted/incorrect counter values under load. Diagnose and fix.
    Answer: Diagnosis: the original code relied on in-process/OS-level locking (e.g., a mutex) to synchronize writes to the shared file — valid only within a single process/machine. After replication across independent instances, each instance has its own OS lock scope; none of them can see or respect another instance's lock, so concurrent writes race and corrupt the file. Fix: replace the local lock with an externally shared, cross-instance lock — e.g., a row-level lock in a database "lock table" representing that file, acquired via a transaction (BEGIN → lock row → modify file → COMMIT to release), which every instance, regardless of which machine it runs on, will honor.

11. Common Mistakes & Misconceptions

  • "Stateless is always slower, so stateful is better for performance." False in aggregate: stateful is faster per cache hit on that specific node, but it doesn't eliminate latency system-wide — it just relocates where the cache lives, at the cost of a scalability/reliability ceiling that stateless designs don't have. A well-placed shared cache closes most of the latency gap without the downsides.
  • "Synchronous replication is strictly 'more correct,' so just use it everywhere." It trades consistency for write availability — using it for every read replica (instead of just a backup) needlessly caps your write throughput at your slowest replica and creates unnecessary availability risk.
  • "Master-master gives better availability, so it's a strict upgrade over master-slave." It removes the single-writer property, and with it the "no write conflicts, ever" guarantee that makes master-slave operationally simple. It's a trade, not a strict upgrade — appropriate specifically for geo-distributed low-latency-write needs, not as a general default.
  • "If I made my service stateless, I don't need to worry about concurrency/locking anymore." Removing session state doesn't remove shared external resource state (files, counters, third-party systems) — those still need cross-instance coordination once replicated (§3.4).
  • "Async replication lag is a bug to be fixed." It's an inherent property of the async design choice, not a defect — the fix isn't "make it faster," it's "choose sync replication for the specific replica where staleness is unacceptable" (i.e., the backup, not every read replica).
