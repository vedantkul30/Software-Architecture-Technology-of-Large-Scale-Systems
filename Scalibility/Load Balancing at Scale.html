Load Balancing at Scale

From a Single Instance to Global Traffic Routing

Syllabus scope: Load balancing multiple instances → Discovery service and load balancing → Load balancer discovery → HLB vs SLB → Layer-7 load balancers → DNS as load balancer → Global server load balancing → Global data replication → Auto scaling instances. This closes out the entire Scalability module.

Assumed baseline: Replication (web/service/DB), specialized services + gateway pattern, asynchronous processing, caching for scalability, vertical/horizontal database partitioning (including master-master replication and its write-conflict trade-offs, from the earlier Replication lecture).

Deferred to later modules (not deep-dived here): The full Micro-Services Architecture module (SOA formalisms, Transactions in Micro-Services, SAGA/compensating transactions, event-driven transactions, NoSQL/Kafka-scale systems) — Doc 15 explicitly defers deeper reliability/failover treatment (disaster recovery, database reliability) to the upcoming Reliability module.

1. Core Concept & Intuition

One-Sentence Definition

Load balancing is the general problem of routing a request to one of many interchangeable instances of a component without the caller needing to track which instances exist or are healthy — a problem solved differently depending on scope (a single service vs. an entire global region), each solution trading off responsiveness, cost, and operational simplicity differently.

Why This Concept Exists

Every scaling technique covered so far (replication, partitioning) produces the same structural side effect: one logical component now has many physical instances, and that instance count changes constantly — instances crash, get added by auto-scaling, or get manually resized. A caller that has to track "which of these 100 IP addresses is currently alive and which one should I use right now" is solving a distributed-systems problem that has nothing to do with its actual business logic. The industry needed a way to decouple "what am I calling" from "which specific instance am I calling" — and needed that decoupling to work correctly at every scale, from a single service's instance pool up to routing users to the correct continent.

Architecture Analogy

Think of a large hospital's central switchboard. A patient calling in doesn't know (and shouldn't need to know) which specific doctor on which specific floor is free right now — they dial one number, and the switchboard (load balancer) figures out who to connect them to, based on who's available and how busy each department is. The switchboard operator also needs to know, in real time, which doctors have clocked in, clocked out, or are on a break (discovery service — who's actually available right now). At a larger scale, imagine the hospital is actually a national hospital network with a flagship hospital in each region — a patient calling a national hotline isn't connected doctor-to-doctor in real time; instead, they're told which regional hospital to go to, based on where they live (DNS/global server load balancing — coarse-grained routing between whole regions, not fine-grained balancing between individual doctors). And when patient volume in one city spikes, the hospital network doesn't wait for a human to notice and hire more doctors — it has a standing policy to automatically bring more on-call staff in when load crosses a threshold, and send them home when it drops (auto scaling).

How a Real System Sees It

  • A client (or gateway service) never holds a raw list of backend IPs long-term. It either talks to a load balancer (which owns and maintains that list) or queries a discovery service directly and applies its own (embedded) load-balancing logic.
  • External clients (browsers, mobile apps) find the system's external load balancer via DNS.
  • Internal clients (service-to-service calls) find internal load balancers or backend instances via static configuration, a discovery service, or an embedded/client-side load balancer.
  • At the network edge, a request may pass through a Layer-4 (transport-level) or Layer-7 (application-level) load balancer, each with different capabilities and cost profiles.
  • At the global level, DNS itself becomes a coarse, region-level routing mechanism, backed by master-master database replication across regions to keep data consistent enough for users to be served correctly regardless of which region they land in.
  • An auto-scaler, fed by a monitoring/health-check system, continuously adds or removes instances and keeps the load balancer's registered instance pool in sync with real capacity.

2. Transcript Content — The "What"

2.1 Load Balancing Multiple Instances — the fundamental problem and its fix

The core problem, stated precisely: A component (e.g., Catalog Service) can have many instances (the transcript's example: 100), and that count fluctuates (90 at one moment, 150 at another). If a caller (e.g., Gateway Service) had to track every instance's IP address directly, it would need to (a) maintain a large, constantly-changing list, and (b) decide which one to call for every request — both are poor responsibilities for a client to own.

The fix — a load balancer provides a single, stable IP address for an entire component. The caller connects to one IP; the load balancer is responsible for:

  1. Knowing the current set of healthy backend instances.
  2. Choosing which instance to route each request to, based on a configurable strategy (round robin, random, etc.).

Where load balancers sit in the architecture (explicit in transcript): every component with multiple instances can be fronted by its own load balancer — web application, gateway service, and each individual microservice (catalog, order, etc.) can each have a dedicated load balancer in front of them.

Load distribution across this chain is uneven (explicit observation): the outermost load balancer (the one with a public IP, facing external traffic) sees the highest load. Internal load balancers (fronting individual services) see comparatively less traffic each, but they still exist because they provide the same convenience — a single, stable point of contact — for whichever component sits behind them, making that component's instance pool easy to administer.

Explicit trade-off acknowledged: fronting every microservice with its own dedicated load balancer is a valid, workable architecture (and is exactly what Kubernetes does by default) — but it's explicitly called out as "one way of doing things," with an alternative (avoiding a dedicated load balancer per service) introduced in the next topic.

2.2 Discovery Service and Load Balancing — the embedded/client-side alternative

The architectural shift: instead of a dedicated load balancer in front of every backend service, per-service load balancers are removed and replaced with:

  1. A Discovery Service (a new, central component).
  2. An embedded load balancer — a library/code embedded directly inside the calling service (e.g., inside Gateway Service), rather than a separate infrastructure component.

The outer-facing load balancers (fronting the gateway service and the web application) remain unchanged — this change applies specifically to internal service-to-service calls.

How Discovery Service works:

  • Every service instance, on startup, registers itself with Discovery Service — announcing its service name (e.g., "Order Service"), its instance ID, and its IP address.
  • Every instance periodically sends a heartbeat to Discovery Service to signal it's still alive.
  • As a result, Discovery Service always knows two things: (a) the full set of services and instances that exist, with their IPs, and (b) which of those instances are currently healthy (based on recent heartbeats).

How the embedded load balancer uses this:

  • When Gateway Service needs to call Order Service, it queries Discovery Service for the current list of healthy Order Service instances (e.g., a list of 100 IPs).
  • The embedded load balancer (a library inside Gateway Service) then applies a configurable strategy to pick one instance from that list and makes the call directly to it.
  • This pattern is symmetric — any service can query Discovery Service and embed this same load-balancing logic to call any other service (e.g., Order Service calling Catalog Service works the same way). A caller isn't strictly required to use a sophisticated strategy — it could even pick randomly from the returned list — but a proper embedded load balancer gives better distribution.

A key generalization (explicit in transcript): Discovery Service isn't exclusive to embedded/client-side load balancing — traditional (dedicated) load balancers can also query Discovery Service to get the current list of healthy instances, rather than relying on static configuration. Discovery Service is thus a shared utility usable by either architectural style.

When you need this, and when you don't: in any large-scale system with many services and many instances per service, tracking availability via static configuration alone becomes impractical — a Discovery Service is the standard answer. Exception: if you're running on Kubernetes, its built-in cluster management already handles this, so a separate Discovery Service may not be needed.

2.3 Load Balancer Discovery — how clients find load balancers themselves

This addresses a subtly different question: not "how does a service find another service," but "how does a client find the load balancer in the first place."

External clients (browsers, external apps):

  • They connect to a DNS name (e.g., www.abc.com), not directly to an IP.
  • DNS resolves that name to the external load balancer's external IP address.
  • The client then connects to that IP, which routes to the load balancer.
  • External clients cannot and do not connect to internal load balancers directly.

Internal clients (services calling other services):

  • They do not use DNS for this. Instead, they use one of two approaches (echoing §2.2):
    1. Static configuration — the internal load balancer's IP address is provided to clients as configuration.
    2. A registry/discovery service — clients query it (as in §2.2) to resolve the target directly, without necessarily going through a dedicated internal load balancer at all.

The clean split, stated explicitly: DNS is the mechanism for external service discovery; static configuration or a discovery/registry service is the mechanism for internal service discovery.

2.4 HLB vs SLB — Hardware vs Software Load Balancers

Two categories:

  • Hardware load balancers (HLB) — physical appliances (the transcript's named example: F5). Support both Layer-4 (L4) and Layer-7 (L7) load balancing.
  • Software load balancers (SLB) — pure software (the transcript's named example: NGINX). Support only L7.

Layer definitions (explicit):

  • L4 (Transport layer): protocols like TCP, UDP, SCTP. No concept of a "request" at this layer — just packets.
  • L7 (Application layer): protocols like HTTP, HTTPS, SMTP, FTP. This is where the concept of a discrete "request" exists.

Quantitative comparison given in transcript (illustrative figures, as presented):

F5 (Hardware) NGINX (Software)
Max connections ~300 million ~225K
Throughput ~160 Gbps (stated as "322,160 GPPS" in transcript, presented as a very high figure) 50–70 Gbps
Requests/sec (L7 only, since L4 has no "requests") ~10 million ~3 million

Key qualitative point: hardware load balancers are dramatically more powerful on raw connection count, but NGINX's requests/sec figure (comparing L7-to-L7, an apples-to-apples comparison) is much closer to the hardware figure than the raw connection-count comparison suggests — meaning software load balancers are far more capable than the headline connection-count gap implies, once you compare the right metric (L7 vs L7).

Why use software load balancers at all, given hardware is more powerful? Cost. Hardware load balancers are extremely expensive. Software load balancers can be free (open source), with optional paid support/subscription — and for many real workloads, their throughput/request capacity is more than sufficient. The explicit guidance: choose based on your actual use case's load requirements; start with software load balancers if they suffice, and upgrade to hardware only when needed.

2.5 Layer-7 Load Balancers — capabilities beyond basic distribution

L7 load balancers, because they operate at the application protocol level, have capabilities L4 load balancers don't:

  1. Act as a reverse proxy — they terminate/break the TCP connection. A client connects to the load balancer (connection 1); the load balancer opens a separate connection to the chosen backend (connection 2). At any moment, two distinct TCP connections exist for a single logical request-response flow. (Contrast: an L4 load balancer can act as a direct router, without necessarily breaking the connection this way — L7 always acts as a proxy, not just a router.)
  2. Content-based routing. Because an L7 load balancer can inspect the actual HTTP request — URL, cookies, body, etc. — it can route different types of requests to entirely different backend pools. Explicit example: a request to a "dynamic action" URL is routed to the web application, while a request for static image content (a different URL, e.g. an images. subdomain) is routed to a separate static content server. This lets you architecturally separate static and dynamic content serving behind a single entry point.
  3. Load-based balancing strategies — same category as L4 (round robin, least connections, weighted round robin, least response time), so L7 doesn't lose any of L4's balancing capability, it adds to it.
  4. SSL termination. Incoming HTTPS requests can have their encryption "terminated" (decrypted) at the load balancer; the request forwarded to the backend can then travel as plain HTTP, saving the backend the computational cost and latency of handling TLS itself.

2.6 DNS as a Load Balancer — the general (non-global) case

DNS's basic job: convert a domain name into an IP address via A records (address records). A single domain can have multiple A records — multiple IPs serving the same name.

The load-balancing opportunity this creates: when a DNS query returns one IP out of several (round robin, or randomly), or returns a full list of IPs, some degree of load distribution results, since traffic isn't always directed to the same single server.

  • A browser typically only uses a single returned IP (it won't do its own selection logic among multiple).
  • A smarter client that receives a full list of IPs can implement its own load-balancing logic on top.

DNS can also do health checks: DNS providers (explicitly: cloud DNS services like Amazon's and Google's) can actively ping backend instances and omit unhealthy ones from their responses — protecting clients from being directed to dead instances.

Why, despite these capabilities, DNS is still explicitly NOT used as a general-purpose load balancer:

  • A true load balancer is an active component that continuously tracks instance health and immediately stops routing to a failed instance the moment it's detected.
  • DNS, by contrast, relies heavily on caching for its own scalability — responses are cached with a TTL (Time to Live), meaning a client may hold a stale mapping and keep sending requests to an instance that's already unhealthy, for as long as the TTL allows.
  • You could lower the TTL to reduce staleness, but TTL = 0 would defeat caching entirely and overload the DNS infrastructure — so a practical TTL must be set, and that practical value is generally too high (not "instant" enough) for DNS to function as a real load balancer.

Verdict: DNS provides load-distribution-adjacent capabilities but cannot do the active, real-time failure detection and rerouting that defines true load balancing.

2.7 Global Server Load Balancing — the one case where DNS-as-load-balancer does work

The reframing: DNS isn't used as a load balancer in general — but it is used as one in the specific case of routing between geographic regions, because the staleness problem that disqualifies DNS at the instance level doesn't apply the same way at the regional level.

Why regional-level DNS staleness is acceptable, when instance-level staleness isn't:

  • Within a region, hundreds/thousands of instances exist behind a load balancer, and individual instances go down frequently — the instance list must update fast and often, or requests will routinely hit dead instances.
  • At the global level, there are only a handful of regions (e.g., North America, AsiaPac), and each region has substantial internal redundancy — a whole region going down is a rare event. Regional liveness data is therefore fairly static over long periods, which is exactly the condition under which DNS's caching-driven staleness becomes tolerable rather than disqualifying.

How it works, mechanically:

  • A user's browser queries DNS for the system's domain name.
  • DNS looks at the user's geographic location and returns the IP address of the nearest/appropriate regional data center (e.g., a North America user gets the North America data center's IP; an AsiaPac user gets the AsiaPac data center's IP).
  • Critically, this is NOT dynamic back-and-forth load balancing — a given user is not shuffled between regions based on momentary load. They are consistently routed to their designated region, unless that region becomes completely unavailable (overloaded to the point of failure, or fully down) — only then does DNS eventually reroute them elsewhere.
  • The transcript is explicit: this is better described as routing, not classic load balancing.

What global server load balancing (via DNS routing) achieves — three explicit benefits:

  1. Scalability — the system can now be hosted across multiple regions simultaneously and serve users globally, rather than forcing all global users to one single region.
  2. Performance — via locality/proximity: users connect to the nearest available region rather than a potentially distant one, reducing latency. DNS can factor in region latency, geographic distance, or even nationality-based routing rules to determine the "closest" appropriate data center.
  3. High availability — if a region goes down or becomes overloaded/unavailable, DNS can (eventually) detect this and reroute affected users to a healthy region.

Why the switchover being slow is actually desirable, not just tolerated: rapid, frequent switching between regions risks data corruption — because regional databases are kept in sync with each other (see §2.8), rapid back-and-forth switching could interleave writes in ways that break that synchronization. The system explicitly wants DNS's switchover to only happen once a region's unavailability is virtually certain — deliberate, conservative switching is a feature here, not a limitation to route around.

Disaster recovery as a related but distinct use case: similar in spirit to the high-availability case (users are diverted to another region if the primary is down) but the fallback region may not be actively running at all — it may need to be started up and have its data freshly loaded before it can serve traffic, so the switchover here is explicitly not quick. (Deeper treatment of disaster recovery is deferred to the upcoming Reliability module.)

2.8 Global Data Replication — keeping regional data in sync so global routing actually works

The setup this section assumes: two (or more) data centers, one per region, each fully capable of serving users independently and simultaneously — this is called an Active-Active setup, where all sites are active at the same time (as opposed to one active site with passive standby sites).

How data stays in sync across regions: Master-Master (Peer-to-Peer) replication between the regions' databases — this is the specific use case the earlier Replication lecture flagged master-master for: independent writes across geographically distant locations.

Within a single region, nothing new: each region has its own standard setup already discussed — a master database, plus read replicas and/or backups, using the same replication patterns (synchronous for backups, generally asynchronous for read replicas) covered previously. What's new is specifically the cross-region link between the two regions' masters.

The write-conflict question, revisited and resolved for two sub-cases:

  • General case: master-master replication carries a real risk of write conflicts, requiring either automatic (business-rule-driven) or manual conflict resolution — this echoes the earlier Replication lecture directly.
  • A conflict-free special case, explicitly illustrated (a ride-booking/Uber-like system): if any given user's writes only ever happen in one region at a time — e.g., a user is physically in AsiaPac today (writes only happen there, then replicate to North America) and flies to North America tomorrow (writes now happen there instead, then replicate back) — there is no possibility of write conflict for that user's data, even though the overall system has many users and multiple active write regions. The conflict risk exists only when the same data could genuinely be written concurrently in two places — not merely because the topology supports multi-region writes.

Why synchronous replication is not used between geographically distant regions (explicit reasoning):

  1. Distance/latency: syncing every transaction across a long geographic distance would make each transaction's write latency very high.
  2. Availability risk: if inter-datacenter connectivity is ever broken, synchronous replication would make transactions impossible to complete at all (since both masters must be reachable) — an unacceptable availability cost.
  3. Conclusion: cross-region master-master replication is, in practice, asynchronous.

The direct consequence of asynchronous master-master replication — possible data loss on regional failure: if North America goes down with some recent changes not yet propagated to AsiaPac, and users are then diverted to AsiaPac (per §2.7), they may not see data they just wrote in North America — a real, acknowledged possibility, not a hypothetical edge case. The explicit guidance: systems must be built with this possibility in mind, with appropriate user communication and recovery processes for when it happens (again, deferred to the Reliability module for deeper treatment).

Why the deliberately slow DNS switchover (§2.7) matters even more here: rapid, premature switching between regions — before a region's unavailability is certain — risks creating exactly the kind of near-simultaneous writes in two places that would trigger write conflicts on top of the already-async, lossy replication. Conservative, confirmed-unavailability-only switching is what keeps the master-master replication model tractable at global scale.

2.9 Auto Scaling Instances

What it is, generically: a framework — homegrown or provided by a cloud vendor — that automatically adjusts the number of running instances of an application in response to detected load, without requiring manual intervention.

Why it's necessary, not optional, at real scale: manual scaling can't react fast enough. Explicit example: if 15 instances are currently running and load is projected to spike sharply within 5 minutes, a manual process cannot provision new capacity in time. Automation also removes the risk of human error in scaling decisions.

Components of the framework (explicit):

  1. Monitoring & health-check system — continuously tracks relevant load signals per instance (CPU usage, network traffic, disk usage, or whichever metric is relevant to the system).
  2. Autoscaler — the decision-making component, continuously fed data by the monitoring system.

The scale-up flow, step by step:

  1. A system administrator configures load thresholds (e.g., "don't exceed 70–80% load on an instance").
  2. The monitoring system continuously reports current load to the Autoscaler.
  3. When load crosses the configured threshold, the Autoscaler pulls a pre-built image (a virtual machine image or container image) from a standard location — using a pre-built image (rather than provisioning from scratch at run time) is explicitly called out as necessary to minimize startup delay.
  4. The Autoscaler starts the new instance, which is assigned a new IP address (and possibly a new name) at run time — the Autoscaler must track this.
  5. Once the health-check system confirms the new instance is healthy and ready to serve traffic, the Autoscaler registers it with the load balancer, and it begins receiving a share of traffic.

The scale-down flow: when the monitoring system reports load has dropped, the Autoscaler waits for a period of time to confirm the drop is genuine and sustained (not a momentary dip) before deregistering and terminating some instances from the load balancer.

3. Deep Technical Explanation

3.1 Why "single IP for a component" is a load-bearing abstraction, not just convenience

The single-IP abstraction that a load balancer provides is doing more architectural work than it first appears. It decouples the caller's dependency graph (which components exist) from the runtime topology (how many instances of each component exist, and where). Without this abstraction, every scaling event (adding/removing instances) would be a change that every caller must somehow learn about and react to — an O(N×M) coordination problem across N callers and M scaled components. The load balancer (or its discovery-service-backed equivalent) collapses this into an O(1) problem per caller: "I know one stable address; someone else's job is to keep it pointing at healthy capacity."

3.2 Why embedded (client-side) load balancing is a genuine architectural trade-off, not a strict improvement

Removing the dedicated per-service load balancer (§2.2) doesn't remove the function of load balancing — it relocates it into every caller. This has real consequences: the load-balancing logic (and its correctness) is now duplicated across every service that embeds it, rather than centralized in one place. The upside is one fewer network hop (client → discovery-service-informed direct call, instead of client → dedicated load balancer → backend) and one fewer piece of dedicated infrastructure to run and scale. The downside is every service must correctly implement and maintain that logic, and Discovery Service itself becomes a new, universally-depended-upon component whose own availability and correctness matters enormously — a shift in where operational risk lives, not a removal of it.

3.3 Why DNS's disqualification as a general load balancer is fundamentally about the caching/liveness mismatch, not a DNS limitation per se

It's worth being precise about why DNS fails as a general load balancer: it isn't that DNS is technically incapable of returning multiple IPs or doing health checks — the transcript is explicit that it can do both. The disqualifying factor is a structural mismatch between DNS's scalability mechanism (aggressive caching) and load balancing's correctness requirement (near-instant failure awareness). DNS scales globally precisely because it can be cached extensively — that's the same property that makes it unsuitable for tracking rapidly-changing instance health. This is a genuine architectural tension, not a solvable bug: you cannot have both "cache aggressively for scale" and "reflect instance health instantly" from the same mechanism.

3.4 Why that same disqualifying factor becomes an enabling factor at the regional level

Section 2.7's key insight deserves to be stated as a general principle: a technique's fitness for a job depends on the rate of change of the thing it's tracking, not on some absolute property of the technique. DNS caching is a liability when tracking hundreds of instances that individually fail often; it's a non-issue when tracking a handful of regions that, as a whole, fail rarely. The same caching mechanism, unchanged, moves from "disqualifying flaw" to "irrelevant, tolerable trade-off" purely because the volatility of the underlying data changed by orders of magnitude. This is a broader lesson applicable well beyond DNS: many techniques that seem globally "wrong" for a fast-changing problem become "right" for a slow-changing version of the same problem.

3.5 Why L7 load balancers being proxies (not routers) is a meaningful architectural distinction

An L4 device can act as a pure router — forwarding packets without necessarily terminating the connection itself. An L7 load balancer, by contrast, must terminate the client connection and originate a new one to the backend, because it needs the entire HTTP request (headers, body) available to make content-based routing decisions — something that isn't fully available mid-stream at the packet level the way L4 operates. This is why SSL termination and content-based routing are only possible at L7: both require the load balancer to actually be an endpoint in the HTTP conversation, not just a packet-forwarding intermediary.

3.6 Why cross-region master-master replication's async-only constraint is a physical, not an engineering, limitation

The reasoning in §2.8 for why synchronous cross-region replication isn't used is worth underlining as a physical, not merely operational, constraint: the speed of light imposes a hard floor on round-trip latency across continental distances, and no amount of engineering sophistication removes that floor. This is different from, say, the earlier lecture's within-a-region synchronous replication trade-off (which was about choosing to accept availability risk for consistency) — at global distance, synchronous replication isn't merely undesirable, it's operationally non-viable for any system with real-time transactional requirements, which is why asynchronous master-master is presented as close to the only practical choice at this scale, not one option among equals.

3.7 Failure cases and hidden complexity

  • Discovery Service as a new critical dependency: if Discovery Service itself becomes unavailable, both embedded load balancers and any traditional load balancers relying on it lose their ability to find healthy instances — its own availability/scaling story matters as much as any other core component's.
  • Stale DNS caching causing real user-facing failures at the instance level — the exact reason DNS is disqualified generally (§2.6); a system mistakenly relying on DNS for fine-grained load balancing would intermittently route users to dead instances.
  • Rapid region flapping causing data corruption — explicitly flagged in both §2.7 and §2.8: switching between regions too quickly, before unavailability is certain, risks near-simultaneous writes to the same data in two regions, triggering write conflicts on top of already-lossy async replication.
  • Auto-scaler flapping (scaling up and down too rapidly) — implicit in the transcript's explicit mention of the Autoscaler waiting before scaling down; without that deliberate delay, a momentary load dip could trigger premature instance termination, only to need to scale back up moments later — wasted churn and startup latency.
  • New-instance cold-start delay — explicitly why auto-scaling relies on pre-built images rather than provisioning from scratch; skipping this optimization would make auto-scaling too slow to be useful for reactive, load-driven scaling.

5. Production System Perspective

  • Kubernetes' native service discovery + load balancing: the transcript explicitly notes Kubernetes handles the "per-service load balancer" pattern (§2.1) out of the box, and that a separate Discovery Service (§2.2) may be unnecessary on Kubernetes — this reflects Kubernetes' built-in Service/Endpoints/kube-proxy machinery doing exactly this job natively.
  • Client-side/embedded load balancing in production: Netflix's historical Eureka (service discovery) + Ribbon (client-side load balancer) combination is a direct, well-known production instance of exactly the pattern in §2.2 — services querying a registry and embedding their own load-balancing logic, which is in fact the architectural lineage this lecture's "Discovery Service + embedded load balancer" pattern is drawn from.
  • F5 and NGINX as named, real production load balancers: F5's hardware appliances are commonly used at the network edge of large enterprises needing L4+L7 capability at extreme scale; NGINX is one of the most widely deployed software L7 load balancers/reverse proxies in the industry, often serving as both a reverse proxy and load balancer in front of web application fleets.
  • Global server load balancing in production: cloud provider offerings like AWS Route 53 (with latency-based and geolocation routing policies) and Google Cloud DNS are direct production implementations of §2.7's region-aware DNS routing, including health-check-based failover between regions.
  • Global active-active data replication: systems requiring true multi-region write availability (e.g., large-scale collaboration tools, global ride-hailing/e-commerce platforms) implement exactly the master-master, asynchronous, active-active pattern from §2.8 — often via purpose-built multi-region databases (e.g., Cassandra's multi-datacenter replication, DynamoDB Global Tables) rather than hand-rolled master-master RDBMS setups.
  • Auto scaling in production: AWS Auto Scaling Groups, Google Cloud's Managed Instance Groups, and Kubernetes' Horizontal Pod Autoscaler are all direct production instances of the monitoring → threshold → Autoscaler → image-pull → register-with-load-balancer flow described in §2.9.

6. System Design Perspective

What this concept affects: Scalability (elastic capacity across instances, regions, and load levels), Availability (region-level failover, health-check-driven instance removal), Performance (locality/proximity routing, SSL termination offload), Reliability (conservative failover to avoid data corruption), Operational complexity (discovery service as new critical infrastructure, auto-scaling automation reducing human error), Cost (hardware vs software load balancer economics).

"If I ignored this concept, what would eventually go wrong?"

  • Without any load balancer/discovery mechanism, every caller would need to track a constantly-changing list of instance IPs itself — an unmanageable, error-prone coupling that breaks the moment instance counts change, which they will, constantly, in any elastically-scaled system.
  • Relying on DNS as a general-purpose, instance-level load balancer would routinely route users to dead instances during the (potentially long) TTL window before stale cache entries expire — a direct, user-facing reliability failure caused by a fundamental mismatch between DNS's caching model and load balancing's need for instant failure awareness.
  • Deploying a single-region system as global traffic grows, without global server load balancing, forces all users worldwide to a single region — inflating latency for distant users and creating a true single point of failure at the regional level.
  • Enabling multi-region active-active writes (for the locality/performance benefits of global routing) without proper master-master replication and conflict-handling discipline risks silent data corruption or lost writes — the benefits of global routing cannot be safely realized without solving the data-sync problem first.
  • Without auto-scaling, a system's capacity is bounded by how fast a human can react to a load spike — for genuinely large-scale systems, this reaction time gap directly translates into dropped requests or degraded service during exactly the moments (traffic spikes) when the system matters most.

7. Performance Analysis

  • Connections vs requests/sec as distinct metrics: the HLB vs SLB comparison (§2.4) is a caution against comparing load balancers on a single headline number — raw connection count (300 million vs 225K) makes hardware look categorically superior, but requests/sec at the L7 layer (10 million vs 3 million) tells a much more comparable story — the right metric depends on what your actual workload looks like (many idle long-lived connections vs high-throughput discrete requests).
  • L7 proxy overhead vs L4 routing: because an L7 load balancer must terminate and re-originate the TCP connection (§2.5, §3.5), it inherently adds a small amount of processing overhead per request compared to an L4 device that can act as a pure router — this is the latency cost paid in exchange for content-based routing and SSL termination capability.
  • SSL termination as a backend latency/CPU optimization: by terminating TLS at the load balancer and forwarding plain HTTP internally, the (often numerous) backend instances are spared the CPU cost of TLS handshakes and encryption/decryption on every request — concentrating that cost at a smaller number of load balancer nodes instead.
  • DNS TTL as a direct latency-vs-staleness dial: lowering TTL improves how quickly clients pick up updated IP mappings (reducing staleness risk) but increases the query load on DNS infrastructure (since fewer responses are served from cache) — TTL = 0 removes caching entirely (unsustainable at scale); a practical non-zero TTL trades some staleness risk for DNS scalability, and this exact trade-off is why DNS's TTL-driven staleness is fundamentally incompatible with instance-level load balancing but tolerable for region-level routing.
  • Pre-built images and auto-scaling latency: provisioning a brand-new instance from scratch (installing software, configuration) at scale-up time would add unacceptable delay during exactly the load spike the auto-scaler is trying to respond to — using a pre-built image (VM or container) collapses this to "pull image + minimal runtime config," directly minimizing time-to-serving-traffic.
  • Cross-region synchronous replication latency floor: as noted in §3.6, the latency cost of synchronous replication across continents is bounded below by physical distance/speed-of-light limits — no amount of software optimization removes this floor, which is precisely why the transcript treats asynchronous replication as close to the only viable option at this scale.

8. Real-World Architecture Examples

Scenario A — A microservices platform choosing between per-service load balancers and embedded discovery-based balancing:
Problem: A system with dozens of services, each with fluctuating instance counts, needs internal service-to-service calls to route correctly without excessive infrastructure sprawl. Chosen: adopt the Discovery Service + embedded load balancer pattern (§2.2) for internal calls, keeping dedicated load balancers only at the external-facing edges (gateway, web app). Trade-off accepted: every service must correctly integrate the discovery-client library, and Discovery Service's own availability becomes mission-critical. Alternative (a dedicated load balancer per service) rejected due to the operational overhead of running and scaling dozens of additional load-balancer instances — though explicitly noted as equally valid, and the default if running on Kubernetes instead.

Scenario B — A global e-commerce platform serving users across continents:
Problem: All global users are currently served from a single region, creating both high latency for distant users and a single point of failure at the regional level. Chosen: deploy active-active data centers in multiple regions (§2.8), route users to their nearest region via DNS-based global server load balancing (§2.7), and use asynchronous master-master replication to keep regional databases in sync. Trade-off accepted: possible small data loss on a rare full-region outage (since replication is async), and deliberately slow (minutes-scale) failover to avoid write-conflict risk from premature switching. Alternative (synchronous cross-region replication) rejected as operationally non-viable given continental distances (§3.6).

Scenario C — A high-traffic web platform separating static and dynamic content at the load-balancing layer:
Problem: A single web-facing endpoint serves both dynamic application pages and static assets (images, CSS/JS), which have very different scaling and caching characteristics. Chosen: an L7 load balancer performing content-based routing (§2.5) — requests for dynamic URLs go to the web application fleet; requests for static-asset URLs (e.g., an images. subdomain) go to a dedicated static-content server/CDN-backed store. Trade-off accepted: the L7 load balancer must terminate and inspect every request (proxy overhead, §3.5) rather than simply routing packets. Alternative (a single undifferentiated backend pool for all traffic) rejected because it would prevent independently scaling and optimizing static vs dynamic serving paths.

10. Interview Questions

Basic

  1. What problem does a load balancer solve for a client that needs to call a component with many instances?
    Answer: Without a load balancer, the client would need to track a large, constantly-changing list of instance IP addresses itself and decide which one to call for every request. A load balancer provides a single, stable IP address for the whole component and takes on the responsibility of routing each request to a healthy instance using a configurable strategy (round robin, random, etc.).
  2. What is the difference between how external clients and internal clients discover the correct load balancer or service instance to call?
    Answer: External clients use DNS — they resolve a domain name to the external load balancer's public IP. Internal clients (services calling other services) do not use DNS for this; they use either static configuration pointing at an internal load balancer, or a discovery/registry service that returns a live list of healthy instance IPs.
  3. Why is DNS generally not used as a load balancer, even though it can return multiple IPs and perform health checks?
    Answer: DNS relies heavily on caching (with TTLs) for its own scalability, meaning clients can hold stale IP mappings and continue sending requests to instances that are no longer healthy. A true load balancer must actively and near-instantly detect failures and stop routing to them — DNS's caching model is fundamentally at odds with that requirement.

Intermediate

  1. Explain why DNS-based routing becomes viable specifically for global server load balancing, even though it's disqualified for general instance-level load balancing.
    Answer: Instance-level load balancing involves many instances that individually fail frequently, making DNS's caching-driven staleness intolerable. At the global/regional level, there are only a handful of regions, each with substantial internal redundancy, so a whole region going down is rare — regional liveness data is fairly static over long periods, which is exactly the condition under which DNS's caching becomes tolerable rather than disqualifying.
  2. Why does a Layer-7 load balancer have to act as a reverse proxy (breaking the TCP connection), while a Layer-4 load balancer can act as a direct router?
    Answer: An L7 load balancer needs to inspect the full application-level request (URL, headers, cookies, body) to make content-based routing decisions and perform SSL termination — this requires it to actually terminate the client's connection and originate a new one to the backend, making it a genuine endpoint in the conversation. An L4 device operates purely on packets/transport-layer information and can forward them without needing to be a full endpoint itself.
  3. Why is synchronous replication generally avoided between database masters located in geographically distant regions?
    Answer: Two reasons: (1) the physical distance introduces high latency for every transaction, since each write would need to wait for acknowledgment from a master far away; (2) if inter-datacenter connectivity is ever broken, synchronous replication would make transactions impossible to complete at all, since both masters must be reachable — an unacceptable availability risk. As a result, cross-region master-master replication is almost always asynchronous in practice.

Advanced

  1. A global platform uses DNS-based routing between two active-active regions with asynchronous master-master replication. During a regional outage, some users report that data they just wrote appears to be missing after being rerouted. Explain why this happens and whether it indicates a bug.
    Answer: This is an expected consequence of the architecture, not necessarily a bug. Because replication between regions is asynchronous (required due to cross-region distance, per Q6), some recently written changes in the failed region may not yet have propagated to the surviving region before the failure occurred. When users are rerouted, they connect to a region that hasn't yet received those changes — a small amount of data loss is an acknowledged, designed-for possibility of this architecture, and systems using this pattern must have processes for communicating this to users and handling the aftermath.
  2. Why does the transcript argue that a load balancer switching users between regions "too quickly" is actually undesirable, rather than simply a limitation to be optimized away?
    Answer: Because regions are kept in sync via asynchronous master-master replication, rapid back-and-forth switching between regions — before a region's unavailability is certain — risks directing near-simultaneous writes for the same data to two different regions in quick succession, which can create write conflicts on top of the already-lossy async replication. The deliberately slow, conservative failover (only switching once unavailability is virtually certain) is what keeps the master-master replication model tractable; a "faster" failover would actually increase the risk of data corruption, not just reduce downtime.
  3. A system architect proposes removing all dedicated per-service load balancers and replacing them entirely with an embedded-load-balancer-plus-Discovery-Service pattern, arguing this is a strict improvement. What trade-offs are being overlooked?
    Answer: The proposal removes one network hop and reduces dedicated load-balancer infrastructure, but it isn't a strict improvement. Load-balancing logic is now duplicated across every service that embeds it, meaning correctness and consistency of that logic must be maintained across every codebase/language that calls another service — a maintenance burden that didn't exist when the logic lived in one centralized load balancer. Additionally, Discovery Service becomes a new, universally-depended-upon component: if it becomes unavailable or degraded, it affects every embedded load balancer across the entire system simultaneously, concentrating risk in a component that previously didn't need to exist. The trade-off is a genuine architectural choice (and the pattern traditional load balancers can also use Discovery Service shows the two approaches aren't even mutually exclusive), not a strict upgrade.

11. Common Mistakes & Misconceptions

  • "DNS can return multiple IPs and do health checks, so it can be used as a general load balancer." Both capabilities are real, but DNS's caching-driven staleness (via TTLs) means it cannot provide the near-instant failure detection and rerouting that defines true load balancing — it's disqualified for general use specifically because of this mismatch, not because it lacks the underlying features.
  • "Global server load balancing works the same way as a normal load balancer, just at a bigger scale." It's explicitly described as routing, not load balancing in the traditional sense — a given user is consistently routed to one region and is not shuffled back and forth based on momentary load, unlike a traditional load balancer's behavior among instances within a region.
  • "Embedded/client-side load balancing is strictly better than dedicated load balancers since it removes a hop." It trades a centralized, single-maintenance-point architecture for one where load-balancing logic is duplicated across every calling service, and it introduces Discovery Service as a new universally-critical dependency — a genuine trade-off, not a strict improvement (see Interview Q9).
  • "Hardware load balancers are always the better choice since their raw numbers are so much higher." The relevant comparison depends on your actual metric of interest — comparing L7-to-L7 requests/sec (not raw connection count) shows software load balancers are far more competitive than the headline numbers suggest, and for many real workloads, cost-effective software load balancing is entirely sufficient.
  • "Master-master replication across regions should use synchronous mode for consistency, just like a local backup replica." Cross-region synchronous replication isn't merely undesirable — the physical distance involved makes it operationally non-viable for real-time transactional systems (unacceptable latency, and total write unavailability on any connectivity break) — this is a different class of constraint than the local, single-region trade-off decision covered in the earlier Replication lecture.
  • "Fast auto-scaling failover/scale-down is always better." The transcript explicitly notes the Autoscaler waits before scaling down, to confirm a load drop is genuine rather than momentary — scaling down too eagerly risks wasteful flapping (terminating and immediately needing to re-provision instances).
