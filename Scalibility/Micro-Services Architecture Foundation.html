Micro-Services Architecture

Motivation, SOA's Limits, and Shared Nothing

Syllabus scope: Micro-Services Motivation → Service Oriented Architecture → Micro-Services Architecture Style.

Assumed baseline: The entire Scalability module — replication, specialized services + gateway pattern, asynchronous processing, caching, vertical/horizontal database partitioning, and load balancing. This lecture explicitly revisits and formalizes the earlier vertical-partitioning content under the name "Shared Nothing Architecture" — treated here as a deeper, named formalization of a pattern already established, not new territory.

Deferred to later lectures (explicitly flagged in-transcript as the next topic, not deep-dived here): Transactions in Micro-Services, Compensating Transactions - SAGA Pattern, Micro-services communication model, Event driven transactions, Extreme scalability with NoSQL and Kafka.

1. Core Concept & Intuition

One-Sentence Definition

Microservices architecture is Service-Oriented Architecture (SOA) taken to its logical extreme — replacing SOA's shared interface schema and shared database with a Shared Nothing design, where every service owns its data and its data-structure definitions exclusively, trading duplicated code/schemas and lost cross-service ACID transactions for genuinely independent development, deployment, and (crucially) truly horizontal database scalability.

Why This Concept Exists

SOA already achieved service-level independence — different services, different tech stacks, independently scalable instance counts. But two forms of coupling silently survived underneath that independence: a shared interface schema (so services agree on data shape) and a shared database (so services can query each other's data directly). Both of these seem like conveniences, but they quietly reintroduce the exact problems specialization was supposed to solve: a schema change in one service can force changes in every dependent service, blocking independent deployment; and a shared database instance can, at best, only be vertically scaled, capping the entire system's database throughput at whatever one machine can do — regardless of how many service instances you run. The industry needed a stricter discipline that removes both forms of hidden coupling entirely, so that "independent service" actually means independent in every dimension that matters for deployment and scalability — not just in code organization.

Architecture Analogy

Think of SOA as several independently run restaurant kitchens that all still share one common walk-in pantry and all agree to use the exact same recipe cards for any dish that crosses between them (e.g., a "sauce" recipe both the pasta station and the grill station use). Each kitchen can hire its own staff, use its own equipment, and cook at its own pace — real independence, on the surface. But the moment the pasta station wants to tweak the shared sauce recipe (interface schema change) or the pantry runs out of shelf space and needs a bigger building (database scaling), every kitchen using that recipe or that pantry is affected — and since there's only one building, you can't add pantry capacity by building a second pantry next door; you can only build a bigger version of the same one (vertical scaling only). Microservices is the decision to give each kitchen its own private pantry and let each write its own recipe cards in whatever format it wants — if the grill station needs an ingredient that's technically "owned" by the pasta station's pantry, it has to formally ask the pasta station for it (a service call), never walk in and grab it directly.

How a Real System Sees It

  • Each microservice owns a dedicated database instance (or at minimum a dedicated schema on physically separate infrastructure) — no service queries another service's database schema directly.
  • Cross-service data needs are satisfied through service-to-service API calls, often orchestrated by an intermediate aggregator/orchestrator service, rather than direct data access.
  • Each service defines its own version of shared concepts (e.g., "an order") independently — the same logical entity can have different field names, different structures, and different numbers of attributes across services, with an orchestrator responsible for transforming data between these independent representations as it flows between services.
  • REST is the typical interface style used, not because REST itself creates loose coupling, but because REST doesn't mandate a shared schema the way SOAP's WSDL/XSD contracts do — it's an enabler of the discipline, not the discipline itself.

2. Transcript Content — The "What"

2.1 Micro-Services Motivation

A common confusion flagged upfront: many teams doing "microservices" actually land somewhere between SOA and true microservices architecture, often without realizing it. Being precise about what each term actually means is the explicit goal before going further.

The organizing question: what is microservices architecture actually trying to achieve, and for whom? The transcript draws a clear distinction between:

  • Primary (external, user-facing) impacts — the actual motivation.
  • Secondary (internal, team-facing) benefits — important, but only because they lead to the primary impacts.

The two primary (external) motivations:

  1. Very high scalability — arising from decentralization and independence (a continuation of everything covered in the Scalability module).
  2. Frequent deployment — the ability to ship incremental features/changes often, which has a direct positive business impact (users get new capability faster).

The internal (secondary) benefits, and — critically — their explicit dependency chain:

  • Independent services → enables independent development (different teams can work on different services without stepping on each other) → enables independent deployment (a service can be released without waiting for every other service to also be ready) → produces frequent deployment (since you're not gated by everyone else's release cycle, you can deploy your service whenever, and as often, as you want).

The explicit logical chain (stated directly in transcript):

Independent development depends on independent services. Independent deployment depends on independent development. Frequent deployment results from independent deployment.

This chain is the core argument of the whole motivation section: the internal properties (independent services → independent development → independent deployment) are not the goal in themselves — they are the necessary mechanism that produces the two external goals (high scalability and frequent deployment) that actually matter to end users and the business.

2.2 Service Oriented Architecture — what it achieves, and where its independence quietly breaks down

Starting point: SOA is presented as the architecture that predates and precedes microservices — the "usual" or "normal" way of building services, in contrast to a monolith.

What SOA gets right — genuine independence in two dimensions:

  1. Independent technology stack per service — explicit example: Inventory Service can be C++ with a SOAP interface, while Order Service and Shipment Service are Java applications. Each service can freely choose its own languages, libraries, and frameworks.
  2. Independent and differentiated scaling — each service can be scaled to its own instance count based on its own load, independent of other services' instance counts (explicit example: 8 instances of Order Service, 3 of Inventory Service, 2 of Shipment Service, adjustable independently, e.g., Order Service going from 3 to 5 instances without touching the others).

Where SOA's independence breaks down — two specific coupling mechanisms:

a) Common interface schema (front-end coupling).

  • Example: Order Service and Shipment Service both deal with "an order." SOA mandates that the definition of "order" (e.g., an XML structure) passed to both services is exactly the same — a shared, common schema.
  • Consequence: disruptive changes — removing fields, renaming fields, restructuring — become effectively impossible without coordinating changes across every service sharing that schema. (Purely additive changes, like adding new optional fields, may still be possible.)
  • Explicit clarification on SOAP's role: SOAP is not the root cause of this tight coupling. The actual cause is the existence of a common schema. SOAP (via WSDL/XSD) is simply the mechanism that conventionally enforces and formalizes that common schema — SOAP "helps in achieving" the common schema, and in doing so, helps create the coupling problem, but is not itself the reason the problem exists.

b) Common database schema (back-end coupling).

  • All these services access the same underlying database — even if that database has multiple distinct schemas (order schema, inventory schema, shipment schema), if any service accesses more than one of those schemas (explicit example: Shipment Service accessing both Order schema and Shipment schema), a dependency exists.
  • Physical consequence: because this is a traditional RDBMS (not a distributed database), all these schemas must live in the same physical machine / single primary RDBMS instance — even though the services themselves can be scaled independently and horizontally (hundreds of Order Service instances, 20 Shipment Service instances), they all connect back to the same single database instance.
  • Change-propagation consequence: changing a database schema (e.g., Order schema) that another service depends on (e.g., Shipment Service reading Order schema) forces that dependent service to also be aware of and adapt to the change.

The resulting deployment consequence — independent development, but NOT independent deployment:
Some changes, unrelated to shared schemas, genuinely can be made and released independently. But any change touching the shared interface schema or shared database schema forces coordinated testing and coordinated release across every dependent service — you cannot deploy that one service's change in isolation. The transcript is explicit and precise here: SOA gives you independent development, but not independent deployment.

The scalability consequence — vertical-only database scaling:
Because all services share a single database instance (a direct restatement of the physical-machine consequence above), and a single RDBMS instance's only scaling lever is vertical scaling (per the earlier Performance/Scalability discussion), SOA's database layer is fundamentally capped at vertical scaling — regardless of how horizontally scaled the service layer itself is.

The clean summary verdict: in SOA, services can be scaled horizontally, but the database can only be scaled vertically — making SOA, as a whole architecture, ultimately bottlenecked at the database in exactly the way the earlier Scalability module described for any single shared database.

2.3 Micro-Services Architecture Style — Shared Nothing Architecture

The organizing principle: Shared Nothing. Microservices achieves its two objectives (high scalability, frequent/independent deployment) by eliminating both of SOA's coupling mechanisms — nothing is shared between services, neither database schema nor interface schema.

How the database side is decoupled — separate database instances per service:

  • Each service (e.g., Inventory Service) gets its own dedicated database instance, holding only its own schema.
  • Direct consequence: Shipment Service, which previously accessed both Order schema and Shipment schema directly, can no longer do so. If it needs Order data, it must request it through Order Service (a service call), not by querying Order schema directly.
  • This is precisely what enables true physical/distributed database scaling, without even needing a distributed database technology: by simply not sharing schemas across services, you can host each service's schema on its own separate RDBMS instance — turning "one big database" into "N independent, separately-scalable databases," which is exactly the vertical-partitioning pattern from the earlier Scalability module, now given its formal name and justification in the microservices context.

How the interface side is decoupled — independent data-structure definitions per service:

  • Where SOA mandated one shared "order" definition across Order Service and Shipment Service, microservices lets each service define its own, entirely independent version — different attribute names, different attribute counts, even a fundamentally different structure.
  • This requires an explicit transformation step somewhere in the system: when Order Service creates an order and that order needs to reach Shipment Service, something has to translate Order Service's format into Shipment Service's format.
  • Who does this transformation — explicitly discussed options, with a practical recommendation: it could be done inside Order Service itself, or inside the calling web application — but for a real, large-scale system, the transcript is explicit that the web application should not be doing this job. Instead, a dedicated aggregator/orchestrator service sits in between: it asks Order Service to create the order, receives the result, transforms it into Shipment Service's expected format, and forwards it to Shipment Service.

The critical, explicitly-repeated clarification about REST's actual role:

  • REST does help create loose coupling — but not by itself. REST simply doesn't mandate a shared schema (unlike SOAP's WSDL/XSD contracts).
  • Actual loose coupling requires someone to write the transformation code between formats — REST is an enabler of that discipline (it doesn't get in the way of it), not the mechanism that creates it.
  • Direct parallel drawn to SOA/SOAP: exactly as SOAP was not "the root of the problem" in SOA (the shared schema was), REST is not "the reason" services are loosely coupled in microservices (the deliberate, independently-defined schemas plus the transformation logic are). This is why REST is the conventional choice in microservices — it's compatible with, not the cause of, the Shared Nothing discipline.

How Shared Nothing is actually achieved architecturally — vertical partitioning by domain:

  • You identify the independent business domains within your application (explicit example: order domain, inventory domain, shipment domain) — domains that represent genuinely independent problems that can be served by genuinely independent systems.
  • You then vertically partition along these domain boundaries — this is the direct mechanism that produces both independent schemas (front-end and database) simultaneously.

One more explicit discipline: no shared reusable libraries containing business logic.

  • If two services share a common library that encodes business logic, a business-logic change in one service can force a corresponding change (and redeployment) in the other — reintroducing exactly the kind of coupling Shared Nothing is trying to eliminate.
  • Explicit exception: utilities. Pure utility code (not tied to business logic) is fine to share, precisely because the reason you'd change a utility is essentially never "a business logic change in one specific service" — utilities change rarely and for reasons unrelated to any single service's domain logic, so sharing them doesn't reintroduce the coupling risk that sharing business-logic libraries would.

The payoff — complete decentralization and total independence → very high scalability:
Achieving Shared Nothing across both the database and interface dimensions is presented as the thing that finally delivers complete decentralization and independence — which is why microservices is specifically reached for when very high scalability is required.

The explicit, important caveat — this is not free, and not for every system:
Microservices architecture is explicitly flagged as not suitable for small applications without huge scalability requirements, because it comes at a real cost. Two costs are named:

  1. Duplicate code and duplicate data-structure definitions — since libraries and schema definitions generally aren't shared, the same logical concept (e.g., an "order") ends up defined and maintained separately in multiple places. The transcript explicitly calls this not the big drawback.
  2. Transactions — explicitly flagged as the real, significant limitation: when a transaction fails or needs to be rolled back, microservices architecture faces a genuine challenge that SOA (with its single shared database) didn't have to the same degree. This is the topic the lecture immediately pivots to next (deferred here, per the scope note above).

3. Deep Technical Explanation

3.1 Why "independent services" alone was never enough — the two-axis coupling insight

The core technical insight tying §2.2 and §2.3 together is that "service independence" is not a single property — it's at least a two-axis property: independence of the data contract (interface schema) and independence of the data store (database schema/instance). SOA achieved independence along technology stack and scaling instance count, but left both the data-contract axis and the data-store axis fully coupled. This is precisely why SOA's services could scale horizontally while its database could not — horizontal service scaling doesn't require touching either coupling axis, but horizontal database scaling absolutely does, because as long as multiple services share one database instance, that instance is a single point of both schema-coupling and physical-machine-boundedness. Microservices' entire technical contribution, reduced to its essence, is recognizing and deliberately severing both axes simultaneously.

3.2 Why eliminating shared schemas enables physical database partitioning "for free," without distributed database technology

It's worth being precise about a subtle but important point in §2.3: microservices achieves genuine physical database distribution without requiring any distributed database technology at all — you don't need a NoSQL database, sharding middleware, or any special infrastructure to get N independently-scalable RDBMS instances. The entire mechanism is: stop letting any service query more than its own schema. Once no service crosses schema boundaries, there is no remaining technical reason those schemas must reside on the same physical machine — the coupling was purely a matter of access pattern, not a physical or technological necessity. This is why the transcript emphasizes this is achieved "without even using any distributed database" — it's a direct, mechanical consequence of removing cross-schema access, connecting straight back to the vertical-partitioning discussion from the Scalability module, now explained from the access-pattern angle rather than the scalability-outcome angle.

3.3 Why SOAP/REST are correctly described as enablers, not causes, of coupling

The transcript makes a deliberately repeated, precise distinction that's easy to get wrong: SOAP does not cause tight coupling, and REST does not cause loose coupling. The actual causal factor in both cases is whether a common schema is mandated. SOAP's WSDL/XSD tooling happens to make defining and enforcing a common schema convenient and idiomatic, so systems using SOAP very often end up with shared schemas as a side effect of following SOAP's conventional patterns — but nothing about SOAP as a protocol requires a shared schema. Symmetrically, REST's convention of exchanging loosely-typed JSON without a mandated shared contract makes it convenient to let each service define its own independent format — but achieving genuine loose coupling still requires someone to actually write the transformation logic between those independent formats; REST doesn't do that work for you, it simply doesn't obstruct it the way SOAP's tooling conventionally does. This distinction matters because it corrects a common but technically imprecise industry shorthand ("SOAP = tightly coupled, REST = loosely coupled") with the actual underlying mechanism.

3.4 Why the utilities exception is principled, not arbitrary

The rule "no shared business-logic libraries, but utilities are fine" (§2.3) follows directly from why shared libraries are dangerous in the first place: the risk isn't code reuse itself, it's that a change trigger in one service's domain (a business rule change) can force an unwanted change and redeployment in another, unrelated service purely because they happen to share code. A utility function (e.g., a string-formatting helper, a generic retry wrapper) has no domain-specific change trigger — it changes for reasons entirely disconnected from any single service's business logic evolution, so sharing it doesn't create the cross-service change-propagation risk that sharing business-logic code does. The distinguishing test isn't "is this code shared" but "does this code's rate and reason for change correlate with any one service's domain decisions."

3.5 Why frequent deployment is a consequence, not an independent design goal

Section 2.1's explicit dependency chain (independent services → independent development → independent deployment → frequent deployment) is worth taking seriously as a diagnostic tool: if a team claims to be "doing microservices" but still can't deploy services independently and frequently, the transcript's own logic says to look upstream in this chain for the actual break — is deployment blocked because development isn't truly independent (shared code)? Is development blocked because the services aren't truly independent (shared schemas)? This reframes "we should deploy more frequently" from a process/tooling goal into a direct diagnostic question about which upstream independence property is actually missing — usually traceable straight back to one of the two SOA coupling mechanisms in §2.2 not having been fully eliminated.

3.6 Failure cases and hidden complexity

  • Partial microservices adoption creates the exact confusion flagged at the outset of §2.1 — a system that removes the shared database but keeps a shared interface schema (or vice versa) is neither true SOA nor true microservices; it inherits some, but not all, of each style's trade-offs, without being clearly diagnosable as either.
  • Orchestrator/aggregator service becomes a new critical, stateful-knowledge-holding component — it now owns the transformation logic between every pair of services whose formats differ, meaning it accumulates real, non-trivial business knowledge about how domains relate to each other, even though the domains themselves remain independent.
  • Transaction failures across services (explicitly flagged as the looming, significant issue) — with each service's database now physically separate, a multi-service operation (e.g., create an order and reserve inventory and schedule shipment) can no longer be wrapped in a single ACID transaction; a failure partway through requires explicit compensating logic that didn't need to exist under SOA's single shared database — this is the direct extension of the "loss of ACID transactions" trade-off first introduced during vertical partitioning in the Scalability module, now framed as microservices' central, defining cost.
  • Duplicated schema definitions drifting out of sync — since the same logical entity (e.g., "order") is independently defined in multiple services, nothing mechanically prevents those independent definitions from drifting in ways that make the orchestrator's transformation logic incomplete or incorrect over time — explicitly named as a real (if secondary) cost.

5. Production System Perspective

  • SOA-era enterprise systems: classic enterprise service-bus (ESB) architectures, often built around SOAP/WSDL contracts and a shared central database (or a small number of shared RDBMS instances), are the direct real-world instance of the SOA pattern described in §2.2 — independent tech stacks and scaling per service, but capped at vertical database scaling and coordinated releases for any shared-schema change.
  • Database-per-service pattern: this is one of the most widely cited, named patterns in real-world microservices practice (often explicitly called "Database per Service") — directly matching §2.3's description of each service owning its own database instance, with cross-domain data access mediated entirely through service APIs.
  • API Gateway / orchestration layer as the transformation point: the aggregator/orchestrator service described in §2.3 (translating Order Service's format into Shipment Service's format) is the same architectural role played by gateway/aggregator services introduced earlier in the Scalability module — production systems (e.g., large e-commerce platforms coordinating order-to-fulfillment handoffs) routinely place this transformation and orchestration responsibility in a dedicated service rather than in the calling client or in either of the two domain services directly.
  • REST as the conventional microservices interface style: the near-universal industry default of REST (over SOAP) for microservice-to-microservice and client-to-service communication directly reflects §2.3's explanation — not because REST inherently creates loose coupling, but because it doesn't obstruct the independent-schema discipline the way SOAP's contract-first tooling conventionally does.

6. System Design Perspective

What this concept affects: Scalability (database dimension specifically — the one axis SOA structurally cannot fix), Deployability (independent vs coordinated releases), Development velocity (team independence), Consistency (loss of cross-service ACID transactions — the major, explicitly-flagged cost), Maintainability (duplicated schema/code as an ongoing maintenance surface), Organizational structure (teams can own services genuinely end-to-end only once Shared Nothing removes cross-service coordination requirements).

"If I ignored this concept, what would eventually go wrong?"

  • Adopting "microservices" in name (separate deployable services) while still sharing a database or interface schema means you inherit SOA's actual limitations — vertical-only database scaling and coordinated, non-independent deployments — while paying some of microservices' organizational overhead (more services to manage) without receiving its actual benefits. This is precisely the "confusion between SOA and microservices" the lecture opens by warning against.
  • Applying full Shared Nothing microservices to a small system without real scalability needs means absorbing the duplicated-code/schema cost and, more importantly, the lost cross-service ACID transaction guarantees — for no corresponding scalability benefit, since the system was never going to hit SOA's database ceiling in the first place.
  • Sharing business-logic libraries across services (rather than only utilities) reintroduces exactly the change-propagation coupling that Shared Nothing is designed to eliminate — a business-logic change in one service silently forces a redeployment obligation on another, defeating independent deployment even if the database and schema are otherwise properly separated.
  • Ignoring the transaction-failure problem (deferred to the next lecture) while still moving to microservices means a multi-service operation can partially fail with no defined recovery mechanism — a correctness gap, not merely an inconvenience, that must be addressed via patterns like SAGA before the architecture is production-safe for any operation spanning multiple services.

7. Performance Analysis

  • Vertical-only vs horizontal database scaling ceiling: SOA's shared single-instance database is bounded by whatever a single machine's CPU/memory/disk can sustain, regardless of how many service instances sit in front of it — this is the direct database-layer analog of the "hardest thing to scale" argument from the Caching lecture, now explained specifically in terms of why SOA cannot escape it (schema sharing forces single-instance hosting) versus why microservices can (no schema sharing removes that forcing function entirely).
  • Cross-service call overhead as the new cost center: every piece of data a microservice needs from another domain, which used to be a direct (and potentially joined, in-database) query under SOA, now requires a network call to the owning service — a latency and throughput cost that didn't exist in the shared-database model. This is an implicit but important performance trade-off: microservices moves cost from "database machine scaling ceiling" to "inter-service network call volume and latency," and whether that trade is favorable depends on how much cross-domain data access the system actually requires.
  • Orchestrator transformation cost: every cross-service data handoff that requires format transformation (Order Service format → Shipment Service format) adds a real, non-zero processing cost at the orchestrator — a cost that scales with the volume of cross-service handoffs, and one that SOA's shared-schema approach didn't incur (since no transformation was needed when both services used the identical schema).

8. Real-World Architecture Examples

Scenario A — An e-commerce platform outgrowing SOA's database ceiling (the transcript's own running example, extended):
Problem: Order, Inventory, and Shipment services are independently deployed and independently scaled in instance count, but all share one RDBMS instance with a shared "order" XML schema (SOA, per §2.2) — the database has hit its vertical-scaling ceiling, and any order-schema change requires coordinated releases across all three services. Chosen: migrate to microservices' Shared Nothing model (per §2.3) — each service gets its own database instance, each independently defines its own "order" concept, and an aggregator/orchestrator service handles the Order-to-Shipment format transformation. Trade-off accepted: cross-service transactions (e.g., "create order and reserve inventory atomically") are no longer possible in the ACID sense — the system must adopt compensating-transaction handling (the next lecture's topic) before this migration is considered complete. Alternative (staying on SOA and further optimizing the single database vertically) rejected because vertical scaling has a hard physical ceiling that horizontal, per-service database scaling does not.

Scenario B — A small internal tool incorrectly over-architected as microservices (a cautionary contrast case, directly per the transcript's explicit caveat):
Problem: A small internal application with modest, well-understood load is built as a full microservices system "because that's the modern way to do it," despite having no real scalability requirement that SOA (or even a monolith) couldn't satisfy. Chosen (correctly, per the transcript's guidance): stick with a simpler architecture (SOA or monolith) instead. Trade-off avoided: the duplicated schema/code maintenance burden and, especially, the loss of straightforward cross-service ACID transactions would have been pure cost with no corresponding scalability benefit for this system's actual load profile — directly matching the transcript's explicit statement that microservices "is probably not suitable for small applications where scalability requirements are not huge."

Scenario C — A platform partially adopting microservices and hitting the "confused middle" the lecture warns about (contrast case):
Problem: A team splits services into separate deployable units and gives each its own database (satisfying the back-end half of Shared Nothing) but continues to define a single shared "order" interface schema used by multiple services (failing to satisfy the front-end half). Consequence: the team gets some of microservices' database-scaling benefit but still cannot deploy services fully independently, since interface-schema changes still force coordinated releases across every service sharing that schema — landing exactly in the "middle part between SOA and microservices" the lecture opens by warning is often adopted unknowingly. Resolution: recognize (per §2.3) that Shared Nothing requires decoupling both the database and the interface schema — introducing an orchestrator/aggregator service to handle per-service independent formats is the missing piece to complete the migration.

10. Interview Questions

Basic

  1. What are the two primary (external) motivations for adopting microservices architecture, according to this lecture?
    Answer: Very high scalability (arising from decentralization and independence) and frequent deployment (the ability to ship incremental changes often, with direct positive business impact). Independent development and independent deployment are internal/secondary benefits that serve as the mechanism producing these two external goals.
  2. What are the two things that create dependencies between services in a Service-Oriented Architecture, even though the services themselves are independently developed and scaled?
    Answer: (1) A common/shared interface schema (e.g., a shared XML "order" definition used by multiple services, often via SOAP/WSDL); (2) a shared database — even if it has multiple schemas, any service accessing more than one schema, or all services being hosted on the same single RDBMS instance, creates a dependency.
  3. What does "Shared Nothing Architecture" mean in the context of microservices?
    Answer: It means nothing is shared between services — no common interface schema (each service defines its own independent data structures) and no shared database (each service has its own dedicated database instance) — eliminating both coupling mechanisms present in SOA.

Intermediate

  1. Why is it inaccurate to say "SOAP causes tight coupling" or "REST causes loose coupling"? What's the actual mechanism?
    Answer: The actual cause of coupling is whether a common/shared schema is mandated between services, not the protocol itself. SOAP's WSDL/XSD tooling conventionally makes defining and enforcing a common schema easy and idiomatic, so systems using SOAP very often end up coupled as a side effect — but SOAP doesn't require this. Similarly, REST doesn't mandate a shared schema, which makes independent per-service data definitions easy — but achieving actual loose coupling still requires someone to actually write the transformation logic between those independent formats; REST doesn't do that work for you, it simply doesn't obstruct it the way SOAP's conventions typically do.
  2. Why can a Service-Oriented Architecture's services be scaled horizontally while its database can only be scaled vertically?
    Answer: Because all services in SOA share a single database instance (even if it contains multiple schemas), and since this is a traditional, non-distributed RDBMS, all shared schemas must physically reside on the same machine. The services themselves have no such constraint — each can run any number of independent instances — but the shared database is architecturally bound to a single instance, which can only be scaled vertically (bigger hardware), not horizontally (more machines), as long as the sharing persists.
  3. Explain why "independent development" does not automatically imply "independent deployment" in SOA, using the concept of schema dependencies.
    Answer: Different teams can develop different services independently day-to-day (different codebases, different tech stacks). But if a change touches the shared interface schema or shared database schema, every service depending on that schema must be updated, tested together, and released together — meaning the service cannot actually be deployed on its own, independent timeline, even though its development process was otherwise independent.

Advanced

  1. A team believes they have adopted microservices architecture because their services are deployed as separate processes with independent codebases, but they still cannot release any single service without coordinating with several other teams. Diagnose the likely cause using the concepts from this lecture.
    Answer: This is very likely the "confused middle" between SOA and true microservices that the lecture opens by warning about. The team has service-level separation (independent codebases/processes) but has likely not achieved Shared Nothing — either a common interface schema, a shared database, or both, still couples their services. Per the explicit dependency chain (independent services → independent development → independent deployment → frequent deployment), the break is upstream: true independent deployment requires eliminating both SOA coupling mechanisms (§2.2), not merely splitting code into separate services.
  2. Why does the lecture explicitly state that shared utility libraries are acceptable under Shared Nothing architecture, while shared business-logic libraries are not — even though both are technically "code reuse"?
    Answer: The distinguishing factor isn't whether code is reused, but whether the code's rate and reason for change correlates with any single service's domain-specific decisions. Business-logic libraries change specifically because a service's business rules evolve — sharing such a library means a business change in one service's domain forces an unwanted, coupled change and redeployment in another, unrelated service, reintroducing the exact coupling Shared Nothing eliminates elsewhere. Utilities (e.g., generic helper functions) change for reasons unrelated to any service's domain logic, so sharing them doesn't create that cross-service change-propagation risk.
  3. A small internal reporting tool with low, predictable traffic is being redesigned. An engineer proposes full microservices architecture "for best practice." Evaluate this proposal using the trade-offs discussed in this lecture.
    Answer: This is very likely a poor fit, based on the lecture's own explicit guidance. Microservices' benefits (very high scalability, frequent independent deployment) are motivated by genuine scalability and deployment-cadence needs that this system — low, predictable traffic — doesn't have. Meanwhile, its costs are real and non-trivial: duplicated schema/code definitions across services, and — the more serious cost — the loss of straightforward cross-service ACID transactions, requiring compensating-transaction handling that a shared-database architecture (SOA or even a monolith) wouldn't need at all. The lecture explicitly states microservices "is probably not suitable for small applications where scalability requirements are not huge" — this system is a textbook case of that caveat.

11. Common Mistakes & Misconceptions

  • "We split our monolith into separate deployable services, so we're doing microservices." Service separation alone is not sufficient — without also eliminating both the shared interface schema and the shared database (Shared Nothing, §2.3), the result is closer to SOA (or an unclear hybrid) than true microservices, and won't deliver independent deployment or horizontal database scalability.
  • "SOAP is the reason our services are tightly coupled; if we just switch to REST, we'll get loose coupling for free." Switching protocols alone doesn't create loose coupling — the actual work is defining independent per-service data structures and writing explicit transformation logic between them. REST merely doesn't obstruct this the way SOAP's contract-first tooling conventionally does; it isn't a substitute for doing the decoupling work.
  • "Our services scale independently, so our whole system scales horizontally." As SOA demonstrates explicitly, service-level horizontal scaling and database-level scaling are separate concerns — a system can have fully independent, horizontally-scaled services while still being capped at vertical-only database scaling if the database itself remains shared.
  • "Code reuse is always bad in microservices." Only business-logic-bearing shared libraries are problematic, because their change triggers correlate with a specific service's domain evolution. Shared utility code, which changes for reasons unrelated to any one service's business logic, is explicitly fine to reuse.
  • "Microservices is strictly a better architecture than SOA, so we should always use it." The lecture explicitly frames this as a trade-off, not a strict upgrade — microservices pays for its scalability and deployment benefits with duplicated code/schemas and, more seriously, the loss of cross-service ACID transactions, making it unsuitable for systems that don't actually need very high scalability.
