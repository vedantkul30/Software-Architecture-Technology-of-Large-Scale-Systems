1. Core Concept & Intuition

One-Sentence Definition

A single logical business operation (like "book an order") that spans multiple microservices — each with its own private database — cannot use a normal ACID database transaction across all of them without destroying the scalability/availability that microservices exist to provide, so instead it's broken into a sequence of independent local transactions coordinated either by locking-based distributed commit protocols (which don't scale) or by compensating transactions (the SAGA pattern), ideally driven asynchronously through events.

Why This Concept Exists

In a monolith, "book an order" touches one database, so a single ACID transaction (BEGIN...COMMIT) trivially guarantees all-or-nothing correctness. The moment you split into microservices — precisely to gain independent scalability (per the previous notes' "decentralization + independence" principles) — you also split the data, and now "book an order" needs coordinated changes across three separate databases owned by three separate services. The industry problem: how do you preserve the illusion of one atomic operation when the underlying reality is now a distributed system with independent, autonomous parts — without reintroducing the tight coupling and locking that microservices were meant to escape in the first place?

Architecture Analogy

Think of booking a vacation package through three independent, separately-run businesses: a hotel, an airline, and a car rental company.

  • Distributed ACID (Two-Phase Commit) is like calling all three, asking each to put a tentative hold on your reservation and wait on the phone (not confirming anything else) until you've heard back from all three — only then do you tell everyone "go ahead, confirm it." This works, but if any one business is slow to answer, everyone else is stuck holding the phone, unable to serve any other customer in the meantime. This doesn't scale if you're a travel agency doing this for thousands of customers simultaneously.
  • Compensating Transactions (SAGA) is like just booking each one in sequence, immediately and independently — hotel first, then flight, then car — and if the car rental turns out to be unavailable, you call back the hotel and airline to cancel what you already booked. Nobody was ever kept waiting on hold; each business could go on serving other customers throughout. The trade-off: for a little while, you genuinely do have a hotel and flight booked with no car — a temporary, real inconsistency that gets resolved (either completed or fully undone) shortly after.

How a Real System Sees It

In the reference "book order" example: a request enters through a Gateway Service, reaches an Order Service, which must coordinate with an Inventory Service (check/reserve stock) and a Shipment Service (arrange delivery) — each with its own database (Order DB, Inventory DB, Shipment DB). What looks like "one transaction" to the end user is actually three separate local ACID transactions, one per service's own database, that must be made to behave as if they were one atomic unit — this is the entire problem this lecture solves.

2. Transcript Content (The "What")

2.1 Synchronous vs. Asynchronous Communication — Setting the Context

Two communication models available for microservices, and the choice directly determines which transaction strategy is viable:

Synchronous Asynchronous
Best for Immediate responses, small reads/small processing — better user experience Write-heavy operations that take time and don't need an immediate response
Reliability Not very reliable — if a service instance is slow or down, the client must retry More reliable/available — defers work rather than failing under load
Behavior under high load Requests time out and fail; retrying under high load is a poor strategy (adds more load to an already-struggling system) Defers processing until load relaxes — doesn't need to complete within a fixed window
Scalability implication Poor fit for long-running, multi-step operations under variable load The scalable strategy for operations (like multi-step order booking) that can take a variable/longer amount of time

🔑 Key takeaway driving everything that follows: because synchronous calls carry timeouts and retry-under-load pitfalls, and because a multi-service transaction can take an unpredictable amount of time to complete (waiting on inventory, shipment, etc.), asynchronous, event-based processing is the scalable and reliable way to implement microservices transactions.

2.2 The Core Problem: One Logical Transaction, Three Local Transactions

Worked example — Order Booking:

Gateway --> Order Service --> checks/reserves --> Inventory Service (own DB)
                          --> checks/arranges --> Shipment Service (own DB)
                          --> confirms          --> Order DB (own DB)
  • Each service doing a transaction against only its own database is a local transaction — fully ACID, just like a monolith talking to its own DB.
  • But the overall "book order" operation spans three separate local transactions across three independently-owned databases — there is no single database to wrap a normal transaction around.

Two approaches discussed: (1) Distributed ACID transactions (via Two-Phase/Three-Phase Commit), and (2) Compensating transactions (SAGA pattern). The lecture's explicit purpose in covering the first is to demonstrate why it fails for microservices, motivating the second.

2.3 Distributed ACID Transactions — Two-Phase Commit (2PC)

Guarantees full ACID properties across all participating services via a two-phase protocol:

Phase 1 — Promise/Prepare:

  • A coordinator (in this example, the Order Service itself acts as coordinator — though a dedicated coordinator service is also possible) asks every participant (Inventory Service, Shipment Service) if they're ready to do the transaction.
  • Each participant takes locks on its database and, if it can proceed, promises the coordinator it's ready.

Phase 2 — Commit (or Rollback):

  • If all participants promised: the coordinator commits its own part and instructs all participants to commit. Once done, a success response goes back to the client.
  • If any participant cannot promise (e.g., Shipment Service can't fulfill): the coordinator issues a rollback to all participants, and every lock/tentative change taken so far is undone. The client receives a rejection.

Why 2PC is rejected for microservices:

  • Locks are held for the entire duration of the two-phase exchange — a long time, across a network, across multiple independently-operated services.
  • These held locks block other requests trying to access the same data.
  • This does not scale. It's suitable only where scalability requirements are low — which directly contradicts the entire reason microservices are chosen in the first place (high scalability). Hence: 2PC is not used in microservices.

Three-Phase Commit (3PC) — mentioned but also rejected:

  • An improvement over 2PC for reliability: 2PC can leave participants blocked indefinitely if the coordinator (or a worker) goes down mid-transaction. 3PC addresses this reliability gap.
  • However: 3PC's scalability problem is not solved — if anything, it's compounded. So despite being more reliable, it's equally unsuitable for microservices' scalability needs.

2.4 Compensating Transactions — The SAGA Pattern

No special framework/library required — just custom code written to implement the pattern (though modern implementations often use orchestration frameworks in practice; the transcript emphasizes it's conceptually just code you write).

"Happy path" example (nothing goes wrong):

1. Order Service creates a temporary order (local transaction, Order DB)
2. Inventory Service reserves inventory (local transaction, Inventory DB) — COMMITTED, not just locked
3. Shipment Service creates shipment (local transaction, Shipment DB) — COMMITTED
4. Order Service confirms the order (Order DB)
--> Success response returned to client

Critical distinction from 2PC: each step is committed immediately — no locks held beyond the scope of that individual local transaction. There's no waiting/holding across services.

The failure case — this is where compensation comes in:
If, say, shipment creation fails partway through (after order and inventory changes have already been committed), the system is now in a "dirty" partial state: real committed changes exist for steps that shouldn't have happened, because the overall transaction can't complete. The fix: undo (compensate for) each already-completed step, in reverse.

Mechanism — write a corresponding "undo" for every forward step:

Forward step Compensating (undo) step
Create Order Undo Create Order
Reserve Inventory Undo Reserve Inventory
Create Shipment Undo Create Shipment
  • When failure is detected, execute the relevant undo steps, working backward from the point of failure.
  • Flexibility noted: undo steps don't have to be executed strictly serially in reverse order — they can potentially run in parallel, or in a different sequence, depending on the situation.

Two additional reliability challenges called out explicitly:

  1. The undo process itself can fail (e.g., a service goes down mid-compensation). When that service recovers, it must be able to resume/retry the specific undo it was in the middle of — not just move on.
  2. The forward transaction can also stall if a service goes down mid-flow. Here there's an actual choice: wait for the service to recover and continue forward, or give up and start undoing. The lecture's stated preference: generally, wait for the service to come back up and continue forward, rather than immediately compensating — compensation should be the fallback when a step genuinely cannot succeed, not the default reaction to temporary unavailability. (When actively compensating/undoing, though, there's no such choice — you must wait for the needed service to come back, since there's no "further undo" option beyond what's already been attempted.)

ACID properties of a SAGA/compensating transaction — a direct comparison:

Property Status Why
Atomicity Effectively preserved (though not "real" atomicity) Individually, each local transaction is atomic, but the overall operation isn't executed as one atomic block. However, because of the forward+compensation design, the end effect is always either "fully committed" or "fully compensated/undone" — giving the appearance of atomicity.
Consistency Eventually consistent Mid-transaction, the system can be in a state where some databases (e.g., Inventory) reflect the change and others (e.g., Shipment) don't yet — genuinely inconsistent at that moment. Once the full flow (forward or compensating) completes, the system becomes consistent again.
Isolation Not isolated Since local transactions commit independently and immediately (not held behind a lock spanning the whole operation), concurrently-running transactions (e.g., processing Order 1 and Order 2 simultaneously) can see each other's partially-completed states and interfere with one another.
Durability Fully preserved Whatever gets committed to a database is durable, exactly as in any normal local ACID transaction.

🔑 Summary label given directly: SAGA transactions are Atomic (in effect), Eventually Consistent, Not Isolated, and Durable — a deliberate, explicit relaxation of full ACID guarantees, traded for the scalability and availability that a locking-based 2PC/3PC approach cannot provide.

2.5 Event-Driven (Asynchronous) Implementation of SAGA

Moves the SAGA pattern from a conceptual sequence of steps into a concrete, scalable implementation using a message queue and an Order Orchestrator.

Key structural change: logically (and possibly physically) separate the Order Orchestrator from the Order Service — the orchestrator's job is purely to drive the sequence of events forward; the Order Service (like Inventory Service and Shipment Service) is just one more participant reacting to events.

Happy-path event flow:

1. Request --> Order Orchestrator
2. Orchestrator publishes "Create Order" event --> Message Queue
3. Order Service (subscriber) receives event --> creates order --> publishes "Order Created" event
4. Orchestrator (subscriber) sees "Order Created" --> publishes "Reserve Inventory" event
5. Inventory Service (subscriber) reserves inventory --> publishes "Inventory Reserved" event
6. Orchestrator sees "Inventory Reserved" --> publishes "Create Shipment" event
7. Shipment Service (subscriber) creates shipment --> publishes "Shipment Created" event
8. Orchestrator sees "Shipment Created" --> sends response back to client ASYNCHRONOUSLY

Two reliability mechanisms baked into this design, both addressing "what if a service crashes at an inconvenient moment":

  1. Idempotency for re-delivered events: if a service processes an event (e.g., creates the order) but crashes before acknowledging the message queue, the queue believes the event wasn't processed and will redeliver it. The receiving service must recognize (e.g., by order ID) that it has already processed this event and simply re-acknowledge without redoing the work — this is an idempotency requirement, explicitly called out as something that must be deliberately built into each service.
  2. Polling as a safety net for the "processed but didn't publish the next event" gap: if a service completes its own local transaction (e.g., order created in the DB) but crashes before publishing the corresponding "done" event to the queue, the next instance that comes up has no in-memory knowledge that this needs to happen. Fix: maintain a status field in the database (e.g., "event not yet published") and have the service poll its own database periodically for records in this state, publishing the missing event once found.

Failure-path event flow (compensation via events):

1-5. Same as happy path, up through "Reserve Inventory" event sent to Inventory Service
6. Inventory Service CANNOT reserve inventory --> publishes "Inventory Reservation Failure" event
7. Orchestrator sees the failure --> begins compensation:
       publishes "Undo Order" event
8. Order Service (subscriber) reverts its changes --> publishes "Order Undone" event
9. Orchestrator sees "Order Undone" --> sends failure notification to client (if required)

Note in this specific example: since inventory reservation itself failed (nothing was reserved), only the order creation step needs compensating — the compensation scope is exactly whatever steps had actually succeeded before the failure point.

Why event-based/asynchronous processing is the right strategy here (restated and reinforced):

  • Under heavy load, event-driven transactions scale much better because they can distribute load over time rather than needing to complete within a fixed synchronous window.
  • Asynchronous transactions have the flexibility to finish in any arbitrary amount of time — a luxury synchronous transactions don't have, since synchronous calls are bound by timeouts and are prone to failing (and prompting poor retry behavior) under load.

3. Deep Technical Explanation

Why 2PC's locking is fundamentally incompatible with microservices' goals

2PC requires every participant to hold a lock from the moment it "promises" until the coordinator's final commit/rollback decision arrives — and that decision depends on hearing back from every participant. This means the duration of the lock is bounded not by that participant's own work, but by the slowest participant in the entire transaction, across a network, across services owned and operated independently. This directly reintroduces the exact problem microservices were adopted to escape (from the Scalability Foundations notes): a form of centralized coordination that creates contention proportional to how many concurrent transactions are in flight — essentially Amdahl's Law and the "coordinator bottleneck" problem from the previous notes, reappearing at the transaction-protocol level.

Why SAGA's relaxed isolation is an acceptable (not just tolerated) trade-off

Full isolation would require preventing any other transaction from seeing intermediate states — which, without 2PC-style locking, isn't achievable. The insight the lecture makes is that this is fine in practice because SAGA guarantees the end state is always either fully-committed or fully-compensated — transient visibility of an in-progress state (e.g., seeing inventory reserved before shipment is confirmed) is a real but bounded and self-correcting condition, not a permanent correctness violation. This is a deliberate trade: sacrifice isolation and immediate consistency to gain the ability for every local transaction to commit and release its resources instantly, rather than holding them hostage to a global decision.

Why idempotency isn't optional, but a structural requirement of at-least-once delivery

Message queues in this design provide at-least-once delivery semantics (a message might be delivered more than once, e.g., due to a crash before acknowledgment) — a much simpler and more robust guarantee to implement than exactly-once delivery, which is notoriously difficult in distributed systems. The trade-off the architecture makes: push the responsibility for handling duplicates onto each consuming service, via idempotency checks (e.g., "have I already processed this order ID?"), rather than trying to solve deduplication at the messaging-infrastructure level. This is why idempotency is described as something you must "build in" — it's compensating for a deliberate simplification made at the infrastructure layer.

Why polling-on-recovery is necessary even with a message queue

A message queue only guarantees delivery of messages that were actually published to it. If a service completes its local database transaction but crashes before publishing the follow-up event, the queue has no idea that event should exist at all — there's nothing to redeliver. This is a gap the queue's own delivery guarantees cannot close, because the failure occurred before the queue was even involved. The polling mechanism (checking the database for "event not yet published" records) is what closes this specific gap — treating the local database, not just the queue, as a durable source of truth for "what still needs to happen."

4. Architecture Trade-offs (The "Why")

Decision Why choose it When NOT to Problems it introduces Alternative
Two-Phase Commit (2PC) Provides genuine, full ACID guarantees across services High-scalability systems (i.e., almost all microservices use cases) Long-held locks block other requests; doesn't scale; coordinator/participant unavailability can block indefinitely Three-Phase Commit (reliability improvement, same scalability problem) or SAGA
Three-Phase Commit (3PC) Improves reliability over 2PC (avoids indefinite blocking on coordinator failure) Same as 2PC — still not scalable, and the scalability problem is described as "compounded" Same scalability issues as 2PC, worse SAGA pattern
Compensating Transactions (SAGA) Scales well; no cross-service locks; each local transaction commits and releases immediately Situations where true isolation or immediate (non-eventual) consistency is a hard business requirement Relaxed isolation (concurrent transactions can interfere); requires writing and maintaining explicit "undo" logic for every forward step; genuinely inconsistent intermediate states are possible Distributed ACID (2PC/3PC) — accept poor scalability for stronger guarantees
Synchronous SAGA orchestration Simpler to reason about immediately Long-running, multi-step, high-load transactions Subject to timeouts; poor retry behavior under load; doesn't scale as well Event-driven/asynchronous SAGA
Event-driven (asynchronous) SAGA Scales by distributing load over time; no fixed completion window; more reliable under load Simple flows genuinely needing an immediate synchronous response Requires building idempotency handling and recovery-polling into every participating service; more complex to implement and reason about Synchronous orchestration (simpler, less scalable)

5. Production System Perspective

  • Uber (ride booking, driver matching, payment): a classic multi-service transaction — booking a ride touches a trip service, a driver-matching service, and a payment service, each with its own data store; well-documented industry discussion around Uber's architecture references SAGA-like compensation patterns for exactly this kind of multi-step, multi-service booking flow.
  • Amazon (order fulfillment): order placement, inventory reservation, and shipment scheduling across independently-owned services is essentially the textbook example this lecture uses directly — Amazon's own publicly-discussed order-processing architecture is widely cited as an origin case for SAGA-style compensating transactions at scale.
  • Stripe (payments): a payment that must coordinate a charge, a ledger update, and a notification to a merchant across separate internal services is a similar multi-step, must-be-reliable-but-can't-lock-everything scenario, motivating similar asynchronous, event-driven, idempotent processing patterns.
  • Netflix (account/subscription changes): changes that ripple across billing, entitlements, and content-access services are commonly implemented with eventual consistency and compensating logic rather than a single cross-service ACID transaction, for the same scalability reasons discussed here.

6. System Design Perspective

  • Scalability: this entire topic is a direct, concrete consequence of the "decentralization + independence" principles from the previous notes — once data is decentralized across services, transactions must also become decentralized (SAGA), or the coordination requirement (2PC) reintroduces exactly the bottleneck those principles were meant to avoid.
  • Reliability: the idempotency and recovery-polling mechanisms are direct reliability engineering — without them, a routine service crash mid-transaction would leave the system in a permanently inconsistent or stuck state; these mechanisms tie forward to later Reliability-module topics (fault detection, recovery) though not yet covered in transcripts.
  • Consistency model as an architectural choice: choosing SAGA is explicitly choosing eventual consistency over strong consistency as a system-wide property for this operation — a decision that must be communicated to and accepted by whoever depends on that operation's guarantees (e.g., a UI must be designed to reflect "order pending" states, not assume instant global consistency).
  • If you ignore this concept and use 2PC/3PC in microservices anyway: you get a system that is architecturally "microservices" in name but behaves like a distributed monolith under load — locks held across service boundaries mean a slow or down service directly blocks unrelated requests elsewhere in the system, eliminating the independent scalability microservices were adopted to achieve.

7. Performance Analysis

  • 2PC lock duration vs. throughput: lock hold time in 2PC scales with the round-trip time to the slowest participant plus the coordinator's decision latency — under load, this compounds, since more concurrent transactions mean more contention for the same locked rows, directly degrading throughput (a distributed-systems instance of the "queue buildup from serial resource access" theme from Module 1).
  • SAGA's throughput advantage: because each local transaction commits and releases resources immediately, there's no cross-service lock contention — throughput scales much closer to the sum of each service's own independent capacity, rather than being capped by the slowest link in a held-lock chain.
  • Asynchronous processing's latency/throughput trade: individual request latency (time to full completion) may actually be higher or more variable under the event-driven model (since it's not bound by a synchronous timeout, and can "take as long as it needs"), but aggregate system throughput under load is much better, since work is spread out over time rather than causing pile-ups and retries.
  • Idempotency check cost: a minor, near-negligible per-event overhead (checking an order ID against already-processed records) — a small performance cost paid to gain robustness against at-least-once delivery duplicates.

8. Real-World Architecture Examples

1. E-commerce order booking with inventory shortage (compensation triggered)

  • Problem: order created and (attempted) inventory reservation, but stock runs out mid-flow.
  • Why SAGA is chosen: allows Order Service and Inventory Service to each operate independently and scale on their own, without holding cross-service locks during the check.
  • Trade-off accepted: a brief window exists where an order record exists in the Order DB with no corresponding successful inventory reservation — resolved shortly after via the undo/compensation event.
  • Failure scenario if 2PC had been used instead: every order attempt would hold locks across both Order and Inventory databases for the full round-trip duration, severely limiting how many concurrent order attempts the system could handle — directly undermining the reason microservices were chosen.

2. A service crash between local commit and event publication

  • Problem: Order Service successfully creates the order in its database, but crashes before publishing the "Order Created" event.
  • Why the polling mechanism is necessary: the message queue has no record of an event that was never published — there's nothing for it to redeliver, so relying on the queue alone would leave this order permanently stuck with the Orchestrator unaware it ever happened.
  • Trade-off accepted: added complexity (a status field, a polling loop) within each service, in exchange for guaranteed eventual forward progress even through crashes.
  • Alternative rejected: relying solely on message-queue delivery guarantees, which don't cover failures occurring before a message is ever published.

3. A message redelivered after a crash right at the acknowledgment step

  • Problem: Order Service processes a "Create Order" event fully, but crashes right before sending the acknowledgment back to the queue — the queue, seeing no acknowledgment, redelivers the same event.
  • Why idempotency is the fix: without it, redelivery would cause a duplicate order to be created for the same request.
  • Trade-off accepted: each service must implement a check ("have I already processed order ID X?") before doing any actual work on a received event.
  • Failure scenario without idempotency: duplicate processing under exactly the kind of transient failure this architecture is otherwise designed to tolerate gracefully — turning a reliability feature (at-least-once delivery) into a correctness bug.

Distributed ACID via Two-Phase Commit:

Phase 1 (Promise):
Coordinator (Order Service) --"can you do this?"--> Inventory Service --(takes locks)--> "I promise"
                             --"can you do this?"--> Shipment Service --(takes locks)--> "I promise"

Phase 2a (all promised -> Commit):
Coordinator --"commit"--> Inventory Service (commits, releases locks)
            --"commit"--> Shipment Service (commits, releases locks)
            --(commits its own part)--> Success response to client

Phase 2b (any refused -> Rollback):
Coordinator --"rollback"--> ALL participants (undo tentative changes, release locks)
            --> Failure response to client

PROBLEM: locks held across the ENTIRE round trip of phase 1 + phase 2 -> blocks other requests -> doesn't scale

HAPPY PATH:
[Create Order]--commit--> [Reserve Inventory]--commit--> [Create Shipment]--commit--> [Confirm Order]
   (each step commits immediately, no cross-service locks held)

COMPENSATION PATH (failure at Create Shipment):
[Create Order]--commit--> [Reserve Inventory]--commit--> [Create Shipment]--FAILS
                                    |                            |
                          [Undo Reserve Inventory] <---- start compensating backward
                                    |
                          [Undo Create Order]
   --> System returns to original state (compensated), failure reported to client

10. Interview Questions

Basic

  1. Why can't a normal ACID database transaction be used across microservices the way it's used in a monolith?
    → Each microservice owns its own separate database; there's no single database to wrap a transaction around. The operation must instead be broken into multiple local transactions (one per service's own DB) that need to be coordinated to behave, in effect, like one atomic unit.
  2. What are the two main approaches discussed for doing transactions across microservices?
    → Distributed ACID transactions (via Two-Phase or Three-Phase Commit) and Compensating Transactions (the SAGA pattern).
  3. Why is Two-Phase Commit generally avoided in microservices architectures?
    → It requires holding locks across all participating services for the full duration of the two-phase exchange, which blocks other requests and doesn't scale — directly undermining the scalability that microservices are adopted to achieve.

Intermediate

  1. Explain the ACID properties of a SAGA-based (compensating) transaction — which are preserved, and which are relaxed?
    → Durability is fully preserved (committed data is durable). Atomicity is preserved in effect (the end result is always either fully completed or fully compensated), even though the process itself isn't executed as one atomic unit. Consistency is only eventual — intermediate states can be genuinely inconsistent until the full flow (forward or compensating) completes. Isolation is not preserved — concurrent transactions can observe each other's partially-completed intermediate states.
  2. What problem does idempotency solve in an event-driven SAGA implementation, and why is it necessary?
    → Message queues typically provide at-least-once delivery, meaning a message can be redelivered if a service crashes before acknowledging it — even if the work was actually already completed. Idempotency (checking whether a given event/order ID has already been processed) prevents this redelivery from causing duplicate processing (e.g., creating the same order twice).
  3. Why does an event-driven SAGA implementation need a polling mechanism in addition to the message queue?
    → The message queue can only redeliver messages it actually received. If a service completes its local database transaction but crashes before publishing the follow-up event, the queue has no record of that event ever needing to exist. Polling the service's own database for records marked "event not yet published" closes this gap, ensuring forward progress resumes even after this specific kind of crash.

Advanced

  1. A service is in the middle of a compensation (undo) flow when it crashes. Explain why this scenario is handled differently from a crash during the forward flow, and what must happen for the system to recover correctly.
    → During the forward flow, the system has a genuine choice on encountering an unavailable service: wait for it to recover and continue forward, or begin compensating. During compensation, there is no such choice — you cannot "give up" on undoing since that would leave the system permanently inconsistent; you must wait for the needed service to recover and then resume exactly the undo step that was interrupted. This requires that each service be able to detect, on recovery, that it was mid-compensation for a specific transaction and resume that specific undo rather than treating it as a fresh, unrelated request.
  2. Why does the lecture argue that Three-Phase Commit doesn't solve microservices' fundamental problem with distributed ACID transactions, even though it improves on Two-Phase Commit?
    → 3PC specifically improves reliability — it prevents participants from being blocked indefinitely if the coordinator or a worker goes down mid-transaction, a real weakness of 2PC. However, it does nothing to address the scalability problem that made 2PC unsuitable in the first place (long-held locks blocking other requests) — and the lecture notes this scalability problem is actually compounded, not fixed, under 3PC. Since scalability is the primary reason microservices are adopted, a protocol that solves reliability but worsens scalability doesn't address the core incompatibility.
  3. Design the compensation logic for a four-step SAGA (Create Order → Reserve Inventory → Process Payment → Create Shipment) where the Process Payment step fails. Walk through what must happen, and identify a subtlety around ordering that the lecture explicitly allows for.
    → On Process Payment failure, the two already-completed steps (Create Order, Reserve Inventory) must be compensated: Undo Reserve Inventory and Undo Create Order. Since Payment itself never succeeded, there's no "Undo Payment" step needed (nothing to undo — mirroring the transcript's own example where a failed Reserve Inventory meant only Undo Create Order was needed, not an Undo Reserve Inventory that never happened). The subtlety: the lecture explicitly notes that compensation steps don't need to run strictly serially in exact reverse order — Undo Reserve Inventory and Undo Create Order could, depending on the system's design, be triggered in parallel or in a different sequence than "last completed, first undone," as long as the end state after all compensations is fully reverted.

11. Common Mistakes & Misconceptions

  • "Microservices should use distributed ACID transactions to guarantee correctness, just like a monolith would." Wrong — this reintroduces cross-service locking that eliminates the scalability benefit of using microservices in the first place; SAGA-based compensation is the standard approach specifically because it avoids this.
  • "Three-Phase Commit is a good middle ground since it's more reliable than 2PC." Wrong per this lecture — 3PC fixes 2PC's reliability weakness (indefinite blocking) but leaves (and worsens) the scalability problem that's the actual reason 2PC is unsuitable for microservices.
  • "SAGA transactions are fully ACID, just distributed." Wrong — SAGA explicitly relaxes both isolation (concurrent transactions can see partial states) and immediate consistency (only eventual consistency is guaranteed); only atomicity (in effect) and durability are preserved.
  • "If a service crashes and comes back up, it's safe to just resume from scratch." Wrong — without idempotency handling, a redelivered event that was already processed can cause duplicate work (e.g., duplicate orders); the service must detect "already done" and simply acknowledge without redoing the work.
  • "A message queue guarantees my whole workflow will complete correctly." Wrong — a queue can only redeliver messages that were actually published to it; a crash occurring before publication (even after a successful local database commit) is invisible to the queue and requires a separate recovery mechanism (polling) to catch.
  • "When a downstream service is unavailable mid-transaction, the safest default is to immediately roll back/compensate." Not quite, per this lecture's stated preference — the general approach favored is to wait for the service to recover and continue forward, reserving compensation for cases where the step genuinely cannot succeed (e.g., inventory is actually unavailable), not merely temporarily unreachable.
