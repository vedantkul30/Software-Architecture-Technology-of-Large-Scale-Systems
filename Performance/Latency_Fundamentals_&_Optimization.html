Latency Fundamentals & Optimization

Course: Developer to Architect | Module 1: Performance | Lectures 9–18 (Serial Request Latency: Network, Memory, Disk, CPU)

(Continuation of 01_Fundamentals_of_Performance.md. Scope note: this closes out "Serial Request Latency" entirely — network, memory, disk, and CPU latency plus their mitigation strategies, and the common latency-cost numbers. It stops before "Concurrency related latency" — Amdahl's Law, Gunther's Law, shared resource contention, locking (pessimistic/optimistic), deadlocks, and coherence all belong to the next notes set, since those are explicitly the "parallel request latency" side of the course and haven't been taught yet.)

1. Core Concept & Intuition

One-Sentence Definition

Serial request latency is the total time a single request spends inside a system — the sum of time lost to network round-trips, memory management overhead, disk I/O, and CPU context-switching — each of which has a distinct physical cost and a distinct mitigation strategy.

Why This Concept Exists

Efficiency (from the prior notes) was the abstract principle; this lecture answers the practical question: where does a single request's time actually go, physically? The industry problem being solved here is that "make it faster" is meaningless without knowing which resource — network, memory, disk, or CPU — is actually consuming the milliseconds. Each of these four resources has wildly different physics (a memory access is ~100,000x faster than a disk seek), so a generic "optimize performance" instruction is useless; an architect needs a resource-by-resource breakdown to know which lever to pull.

Architecture Analogy

Think of a single request as a delivery order fulfilled by a warehouse-to-doorstep logistics chain:

  • Network latency = the actual road trip between warehouse and customer (and the paperwork/toll-booth checks — connection setup — before the truck can even leave).
  • Memory latency = how efficiently the warehouse staff can grab items from nearby shelves (fast) vs. having to run to a distant overflow storage room (slow) vs. running out of shelf space entirely (crash).
  • Disk latency = going all the way to a locked archive basement for items not on the shelves — slow, and especially slow if you have to make several separate trips (random access) instead of one trip that grabs everything in one route (sequential access).
  • CPU latency = the worker being pulled off your order to help with someone else's (context switching) instead of finishing your order start-to-finish.

How a Real System Sees It

Inside the reference system (browser → web app → business service → RDBMS), a single request physically incurs, in order:

  1. Network: browser↔web app connection (persistent HTTP/1.1 ideally), web app↔service call (HTTP or RPC), service↔DB call.
  2. Memory: object allocation on each hop's heap, GC pressure, DB buffer pool usage for the record being read/written.
  3. Disk: DB reading/writing the actual row from/to disk (unless cached), reverse proxy serving static assets from disk/page cache.
  4. CPU: actual computation, plus every time a thread blocks on I/O and gets context-switched out.

2. Transcript Content (The "What")

2.1 Framing: Serial vs. Parallel Latency

Two categories of latency exist, mapped to the two principles from the previous lecture: efficiency → serial request latency (this lecture's focus) and concurrency → parallel/concurrent request latency (next lecture's focus, covering queuing and coherence).

2.2 Network Latency

Two network contexts, with very different characteristics:

Internet (browser ↔ web app) Intranet (service ↔ service, service ↔ DB)
Distance Long-distance, multiple hops/networks Local, data-center scale
Reliability Not fully reliable More reliable (not 100%)
Speed Slower Faster

Two sources of network latency:

  1. Data transfer latency — physical time for data to travel wire-to-wire. Different for internet vs. intranet.
  2. Connection creation latency — the overhead of establishing a TCP connection (all discussion here is TCP-scoped; UDP is faster but not reliable, and reliability would have to be built into the application, so it's out of scope). Any protocol layered on TCP (e.g., SOAP/HTTP-based protocols) inherits TCP's connection overhead.

TCP connection overhead — worked example:

Client --- SYN (50ms) ---> Server
Client <-- SYN-ACK (50ms) --- Server
(ACK + data can be piggybacked — not extra overhead)

Total connection overhead = 1 full round trip = 100ms

If an actual request/response also takes 100ms, total time with connection creation = 200ms → 100% overhead just from connection setup.

SSL/TLS connection overhead — worked example:

1 round trip  -> TCP connection
2 round trips -> TLS handshake (key exchange + cipher/encryption parameter negotiation)
-------------------------------------------------
3 round trips total = 300ms (at 100ms/round trip)

If the actual request/response takes 100ms, total time = 400ms → 300% overhead. This is explicitly called out as particularly costly, especially across multiple calls.

2.3 Minimizing Network Latency

A. Connection overhead → reuse connections, don't recreate them:

  • Connection pooling: business service holds a pool of DB connections; web app holds a pool of HTTP connections to the REST/business service. Reused across requests instead of creating new ones each time.
  • Persistent connections (browser ↔ web app): HTTP/1.1 creates persistent connections by default — multiple sequential calls from a browser to the same server can reuse one connection.
  • Persistent connections matter especially for: (a) any HTTP client library used for service-to-service calls, and (b) internal microservice-to-microservice HTTP communication — the client library must be configured to use persistent connections, or this benefit is lost.
  • SSL session caching: server caches the negotiated encryption parameters for a known client, allowing a shortcut (fewer round trips) on subsequent SSL connections from that same client.

B. Data transfer overhead → reduce or eliminate it:

  1. Caching (flagged as a major topic for later, deep-dive still pending):
    • Service-side: cache DB query results that don't change often.
    • Web app-side: cache user-session data instead of re-fetching.
    • Browser-side: cache static assets (JS, images, CSS).
  2. Efficient (binary) data formats / RPC protocols for intranet communication where interoperability isn't required: gRPC, Thrift, (historically IIOP/EJB). Trade-off: using a binary protocol technically means the service is no longer RESTful (REST implies text-based, interoperable HTTP semantics) — architecturally it becomes a plain RPC service. This is fine internally, but internet-facing services need REST/HTTP's interoperability, so binary protocols are reserved for internal, high-volume communication.
  3. Compression: compress response/request payloads (e.g., gzip). Adds CPU cost to compress/decompress, but that cost is generally much smaller than the data-transfer cost saved — especially over the internet.

2.4 Memory Latency

Four memory-related performance problems:

  1. Finite heap memory — any process is capped by available memory; exceeding it crashes the process.
  2. Garbage-collector aggressive behavior near memory exhaustion — as a GC-managed process (Java, .NET) approaches its memory limit, the GC runs very aggressively, tanking performance for the duration.
  3. Large heap memory:
    • If heap size exceeds physical RAM → OS swaps memory to disk → severe performance hit.
    • Even with abundant physical RAM, a very large heap means the GC has to sweep a much larger space → slower GC → slower system.
  4. GC algorithm mismatch — different GC algorithms are optimized for different workloads; using the wrong one for the situation (e.g., large-data batch processing) hurts performance.
  5. Finite DB buffer memory — every DB read/write happens by first loading the record from disk into memory (buffer/cache), modifying it there, then writing back. Buffer memory space directly governs DB throughput (operations/second). Buffer shortage (due to poor allocation or inefficient schema) severely hurts overall system performance.

2.5 Minimizing Memory Latency

  1. Avoid memory bloat:
    • Smaller code base → less back-and-forth between RAM and processor.
    • Smaller heap footprint → less GC work, lower risk of OOM. (Acknowledged: often outside full architectural control, but avoid unnecessary object allocation wherever possible.)
  2. Weak and soft references (e.g., in Java): mark large, non-critical objects as weak/soft references so the GC can reclaim them under memory pressure. Application must check for null/reclaimed references before use.
  3. Prefer multiple smaller processes over one giant process: e.g., a 40GB-heap JVM (even with 50GB RAM available) makes GC perform badly simply due to sheer heap size. Common fix for batch processing: split work across multiple nodes/JVMs rather than one massive process.
  4. Choose GC algorithm to match workload:
GC type Best for Characteristic
Throughput-oriented (stop-the-world style) Batch processes Efficient overall, but has pauses — acceptable since no live user is waiting
Low-pause / concurrent GC Live/server processes Runs alongside the main process; much smaller pause times — critical because a multi-second pause on a live request-serving JVM would badly hurt many concurrent requests
  1. DB buffer memory optimization:
    • Normalization: avoids duplicate data → less storage needed → more data fits in buffer memory → better DB performance. Default choice.
    • Denormalization: sometimes done for faster reads (avoiding complex joins) — a deliberate trade-off against the "normalize by default" rule, adopted for performance reasons.
    • Compute over storage: if a value can be derived from raw data via business logic, don't store it — avoids unnecessarily occupying buffer memory (disk space itself isn't the concern; buffer memory is). Trade-off: added computation cost vs. relieved memory pressure — worth it when the DB is under memory pressure.

2.6 Disk Latency

Disk I/O is one of the slowest I/O types in the system. Nearly every component does some disk I/O (at minimum, logging). The highest-impact areas: web applications (serving static content from disk) and databases (all reads/writes ultimately touch disk).

2.7 Minimizing Disk Latency

A. Logging:

  • Logging is sequential write I/O, not random I/O — and sequential I/O is far faster than random I/O. So logging is not inherently as slow as it might seem.
  • Batch log writes: combine multiple log statements into one write instead of interleaving computation and logging repeatedly (each interleaving = a context switch).
  • Prefer asynchronous logging: offload logging to a separate thread so the main computation thread never leaves the CPU to perform log I/O.
    • Downside: on a crash, the last few unflushed async log statements may be lost. Acceptable trade-off unless the logged data is mission-critical.

B. Web content (static file) latency:

  • Static files (images, JS, CSS, HTML) live on disk and are fetched frequently — costly if fetched from disk every time.
  • Fix: web content caching via a reverse proxy (e.g., Nginx, Varnish) — separates responsibility: reverse proxy serves static content (from memory if possible, else disk), web application handles only dynamic content.
  • Reverse proxies additionally benefit from page cache (OS keeps recently-read files in RAM even without explicit caching) and zero-copy (kernel-mode file-to-network transfer, skipping user-mode copying) — named but not deep-dived here.

C. Database disk latency:

  1. Cache read-heavy/rarely-changing data outside the DB (in the service's own cache) to avoid hitting the DB/disk at all.
  2. Denormalization (situational): when load testing reveals disk I/O — not memory — as the actual bottleneck, denormalizing data that's spread across multiple tables into one table avoids the extra disk seeks/rotations of multi-table joins. (Default is still to normalize; denormalize only when disk I/O is proven to be the constraint.)
  3. Indexing: without an index, finding a row requires a full table scan (worst case). With a correct index on the filter criteria, the DB goes directly to the record's disk location — drastically less I/O. Poor/incorrect indexing is still a common inefficiency even when some index exists.
  4. Query optimization: write queries that fetch the minimum data necessary (goes hand-in-hand with schema/index optimization; depth deferred as a developer-level concern).

D. Hardware-level disk optimization:

  • SSD over HDD wherever disk I/O is critical — costlier but far lower latency.
  • High-IOPS disks for workloads with heavy random seeks.
  • RAID (Redundant Array of Independent/Integrated Disks) — striping (partitioning) and mirroring (replication) of data across multiple disks, conceptually parallel to partitioning/replication in distributed computing. RAID doesn't reduce the latency of a single operation, but it parallelizes I/O, reducing overall time consumed across many operations.

2.8 CPU Latency

Two causes:

  1. Inefficient algorithms — a developer-level concern, largely out of scope for this architecture-focused module.
  2. Context switching — the architecturally significant one, discussed in depth.

How context switching hurts performance (mechanism):

[Process 1 running on CPU]
        |
        | Process 1 initiates I/O (disk/network/etc.)
        v
OS evicts Process 1:
  - saves Process 1's process control block (PCB) to memory
  - loads Process 2's PCB from memory onto the CPU
        |
        v
[Process 2 now running on CPU]

The gap between "Process 1 stops" and "Process 2 starts" is pure overhead — wasted time that wouldn't exist if the I/O-triggered eviction hadn't happened. If a process gets evicted 2–3 times during what should be a 100ms execution, it can end up taking ~200ms — a direct, compounding performance cost. This applies identically to thread-level context switching, not just process-level.

2.9 Minimizing CPU Latency (Context Switching)

  1. Batch I/O / Async I/O: combining multiple DB calls (or file writes) into one call reduces both network latency and the number of context switches, since the thread doesn't have to evict-and-resume once per call.
  2. Async logging in a separate thread (same technique as in the disk-latency section): keeps the main thread from ever leaving the CPU for log I/O.
  3. Single-threaded event-loop model (Node.js, JS engines like Chrome's V8, Nginx, and other single-threaded-core designs):
    • One main thread handles all request processing; when it needs I/O, it delegates that I/O to separate async worker threads and continues; results come back to the main thread asynchronously.
    • Net effect: the main thread is always doing some request's CPU work — it's never evicted for I/O, since I/O is entirely offloaded. Highly effective under high request volume with heavy I/O.
  4. Right-size the thread pool: too many threads relative to available CPUs (e.g., 100–200 threads on a 2-CPU machine) causes excessive context switching as the OS constantly rotates CPU time among starved threads. No universal number — depends on I/O-vs-CPU-intensity of the workload; this must be tuned per workload (full treatment deferred to a later multi-threading module).
  5. Virtualized/isolated environments per process: when running multiple processes on one large machine, an efficient/hoggish process can starve others of CPU time. Running each process in its own virtual environment (dedicated CPU/memory quota) prevents this interference. General preference: one primary process per machine where performance is critical; multiple processes only on large machines, isolated appropriately.

2.10 Common Latency Costs (Order-of-Magnitude Numbers)

(From a widely-cited 2012 "latency numbers every programmer should know" style reference — absolute numbers have shifted since, but the relative comparisons remain instructive.)

Operation Approx. Latency
CPU cycle / register-level operation 0.5 – 7 ns
Taking a lock (higher than raw CPU ops — cost of contention)
Main memory access ~100 ns
Intra-datacenter network round trip ~500 μs (0.5 ms)
Internet round trip (e.g., California ↔ Netherlands) ~150 ms
Disk seek ~10 ms
Sequential read of 1 MB from disk (incl. 1 seek) ~20 ms
Sequential read of 1 MB from SSD ~1 ms
Compressing 1 KB of data ~3 μs
Sending 1 KB over a 1 Gbps network ~10 μs

Key relative takeaways explicitly drawn out:

  • Internet round trip is ~300x costlier than an intra-datacenter round trip — a first-principles reason to minimize cross-internet calls and batch them when unavoidable.
  • Random disk access (5 seeks ≈ 50ms) is far costlier than sequential access (1MB sequential read ≈ 20ms, one seek) — direct justification for "prefer sequential/batched disk access."
  • SSD sequential read is ~20x faster than HDD sequential read.
  • Compression cost (microseconds) is negligible next to the network cost it saves (especially over the internet) — justifies "always compress data sent over the network."

3. Deep Technical Explanation

Why TCP/TLS handshakes cost exactly 1 and 3 round trips

TCP's 3-way handshake (SYN, SYN-ACK, ACK) requires only 1 full round trip before data can flow, because the final ACK can be piggybacked with the first data segment. TLS adds a negotiation phase on top (cipher suite agreement, key exchange, certificate validation) that costs 2 additional round trips in the classic TLS handshake model — hence 3 round trips total for an HTTPS connection versus 1 for plain TCP. This is precisely why connection reuse (pooling, persistent connections, session caching) has such an outsized effect on latency for encrypted, chatty communication patterns.

Why sequential disk I/O vastly outperforms random I/O

A spinning disk (or even an SSD to a lesser extent) incurs a "seek" cost to reposition before each I/O operation. Sequential access amortizes one seek cost over a large contiguous read; random access pays the seek cost per operation. This is a physical/mechanical constraint for HDDs (armature repositioning) and a lesser but still real constraint for SSDs (internal addressing/erase-block behavior) — which is why "batch and sequence your disk access" is a universal recommendation regardless of storage medium, just with different magnitudes.

Why GC pause behavior differs by workload type

Batch-oriented GCs optimize for total throughput — they can afford to stop the world for a chunk of time because nothing else is waiting on that process's responsiveness. Live-process GCs optimize for pause-time minimization, trading some total efficiency to keep any single pause short enough that it doesn't create a visible latency spike for concurrently-executing user requests. This is the same efficiency-vs-latency trade-off pattern that recurs throughout the module (batch = throughput matters, request/response = latency matters).

Why the single-threaded event-loop model works despite sounding counter-intuitive

It seems paradoxical that fewer threads could be faster, but the model works because the bottleneck it targets is context-switching overhead, not CPU parallelism. In I/O-heavy workloads, most "concurrency" isn't CPU-bound — it's waiting-bound. By keeping exactly one thread perpetually busy with CPU work (and shunting all I/O to worker threads that don't compete for the same execution context), the design eliminates the eviction/restoration cost that a naive one-thread-per-request model would pay repeatedly. This is precisely why Node.js and Nginx outperform naive thread-per-connection servers under high concurrent I/O load — not because they do less work, but because they waste less time on the OS-level bookkeeping around that work.

5. Production System Perspective

  • Stripe / banking-grade APIs: TLS handshake cost is exactly why payment APIs push hard for connection reuse (keep-alive pools) and TLS session resumption — a payment SDK re-establishing a fresh TLS handshake on every call would add hundreds of milliseconds of pure overhead per transaction.
  • Netflix (CDN + static assets): the reverse-proxy pattern for separating static content (images, subtitle files, thumbnails) from dynamic API responses is exactly the "reverse proxy serves static, app serves dynamic" split described here, scaled globally via CDN edge nodes instead of a single reverse proxy box.
  • Node.js at LinkedIn / Netflix's own mobile API gateway: both are well-documented real adopters of the single-threaded, event-loop model specifically because their workloads are I/O-heavy (many downstream service calls per request) rather than CPU-heavy.
  • Discord / real-time chat systems: heavy use of async, batched writes for message logging/persistence — exactly the "batch log statements, use async I/O" pattern — because a chat server can't afford per-message synchronous disk writes at scale.

6. System Design Perspective

  • Scalability: knowing which resource (network, memory, disk, CPU) is actually saturated tells you what to scale — adding CPU cores doesn't help a disk-I/O-bound database, and adding disk capacity doesn't help a context-switching-bound web tier.
  • Reliability: memory mismanagement (large heaps, GC thrashing) is a common root cause of cascading failures — a GC pause on one node can trigger health-check failures and unnecessary failovers.
  • Cost optimization: SSD/RAID/high-IOPS hardware is a direct cost lever that should be applied surgically (hot paths only), not uniformly, based on measured disk-latency data.
  • If you ignore this concept entirely: you'll misattribute performance problems — e.g., blaming "the network" when the real cost is unindexed DB queries doing full table scans, or blaming "slow code" when the real cost is a needlessly re-established TLS handshake on every call. Without a resource-by-resource latency model, optimization becomes guesswork.

7. Performance Analysis

  • Network: connection-establishment overhead scales badly with call frequency — 3 round trips per TLS handshake becomes catastrophic if a service makes many small, unpooled calls; the fix (pooling/persistence/session caching) is purely architectural, not code-level.
  • Memory: GC pause frequency and duration is a direct function of heap size and object churn rate — very large heaps trade "less frequent OOM risk" for "much longer/more frequent GC pauses," so heap sizing is itself a latency-vs-safety trade-off.
  • Disk: IOPS and sequential-vs-random access pattern dominate disk-bound latency far more than raw disk speed rating does — an application generating random access patterns will underperform even on fast hardware.
  • CPU: context-switch cost is proportional to the frequency of blocking operations per unit of useful work — a thread that blocks on I/O 10 times to do 100ms of actual work pays disproportionately more overhead than one that batches the same I/O into 1–2 blocking calls.

8. Real-World Architecture Examples

1. Payment gateway making repeated calls to a fraud-detection microservice

  • Problem: each fraud check was implemented as a fresh HTTPS call.
  • Why architecture matters: 3 round trips of TLS overhead per call, multiplied across every transaction, dominates total latency.
  • Trade-off accepted: introducing a persistent connection pool + SSL session caching adds slight complexity (pool sizing, connection health checks) in exchange for eliminating repeated handshake cost.
  • Alternative: switch fraud-check traffic to an internal gRPC service (binary protocol, persistent HTTP/2 connections) since it's intranet-only and doesn't need REST interoperability.
  • Failure scenario: if the connection pool is undersized under peak load, requests queue for a connection — reintroducing the exact "serial resource access" queue-buildup problem from the prior lecture, just at the connection-pool layer.

2. High-traffic content site serving images/CSS/JS directly from the application server

  • Problem: every static asset request hits the same process that also serves dynamic page content, competing for the same disk I/O and CPU.
  • Why this architecture was chosen (originally): simplicity — one app server does everything.
  • Trade-off once fixed: introducing a reverse proxy (Nginx/Varnish) in front, serving static content from memory/page cache, frees the app server to focus purely on dynamic logic. Adds an extra hop/component to operate.
  • Failure scenario without the fix: disk I/O for static files competes with, and degrades, the latency of dynamic (often revenue-critical) requests.

3. Analytics batch job with a single massive JVM process

  • Problem: one JVM configured with a very large heap (tens of GB) to process a full day's data in one pass.
  • Why this seems reasonable: "we have the RAM, so use it."
  • Trade-off exposed: GC sweep time scales with heap size — a 40GB heap makes even a throughput-oriented GC algorithm slow, and pauses stretch out, delaying the whole batch's completion.
  • Alternative: split the batch across multiple smaller JVM processes/nodes — each with a modest, GC-friendly heap size, processing partitions of the data in parallel.
  • Failure scenario: if left as one giant JVM, an unexpected data volume spike risks pushing heap use past physical RAM, triggering swapping — a severe, sudden performance collapse rather than a graceful slowdown.

10. Interview Questions

Basic

  1. Why is establishing an HTTPS (TLS) connection significantly more expensive than a plain TCP connection?
    → TCP needs 1 round trip (SYN/SYN-ACK, with ACK piggybacked). TLS adds a negotiation phase (cipher suite agreement, key exchange, certificate validation) requiring 2 more round trips — 3 total. Over a high-latency link, this overhead can exceed the actual request's own processing time.
  2. Why is sequential disk access so much faster than random disk access?
    → Each I/O operation pays a seek cost to reposition before reading/writing. Sequential access amortizes one seek cost over a large contiguous read; random access pays the seek cost per operation.
  3. What causes CPU context-switching overhead, and why does it hurt performance?
    → When a process/thread performs blocking I/O, the OS evicts it (saving its process control block) and loads another process's state onto the CPU. The save/restore cycle itself consumes time that contributes nothing to actual request processing — pure overhead layered on top of the real work.

Intermediate

  1. A service makes 10 small, separate calls to another internal service per request, each over its own new connection. What are the two distinct latency costs being paid here, and how would you fix each?
    → (1) Connection-creation overhead paid 10x — fix with connection pooling/persistent connections. (2) Multiple separate context switches and network round trips from unbatched calls — fix by batching the 10 calls into one call where possible (also reduces both network and CPU latency simultaneously).
  2. When would you choose to denormalize a schema, given that normalization is the general-purpose default?
    → Only when load testing specifically shows disk I/O (not memory) as the bottleneck, and the I/O cost comes from multi-table joins that a single denormalized row would eliminate. It's a targeted fix for a proven bottleneck, not a default design stance.
  3. Why might a single-threaded, event-loop-based server (e.g., Node.js/Nginx) outperform a traditional thread-per-request server under high concurrent I/O load, despite using "less parallelism"?
    → The bottleneck in I/O-heavy workloads is context-switch overhead from threads blocking and being evicted, not raw CPU parallelism. A single perpetually-busy main thread delegating I/O to separate async workers avoids repeatedly paying that eviction/restoration cost, which a naive one-thread-per-request model pays constantly.

Advanced

  1. A batch analytics job uses one JVM with a 40GB heap on a machine with 50GB RAM. It's technically within physical memory limits, yet performance is poor. Why, and what would you change?
    → Even without swapping, GC sweep time scales with heap size — a 40GB heap means the garbage collector has to traverse a huge object graph, causing long/frequent pauses regardless of available RAM. Fix: split the batch across multiple smaller JVM processes/nodes with moderate, GC-friendly heap sizes rather than one oversized process.
  2. You need to choose a GC strategy for two different systems: a live, request-serving API, and a nightly batch ETL job. How do the choices differ, and why?
    → The API needs a low-pause, concurrent GC (small, frequent pauses) because a multi-second stop-the-world pause would badly delay many concurrently waiting user requests. The batch job can use a throughput-optimized GC with longer pauses, because total completion time — not per-request latency — is what matters; nobody is waiting on an individual "response."
  3. Given the latency numbers (internet RTT ~150ms, intra-DC RTT ~0.5ms, disk seek ~10ms, SSD sequential read ~1ms/MB), how would you prioritize optimization effort for a service that makes cross-region internet calls to a partner API, and separately does heavy random reads from a local HDD-backed database?
    → The internet round trip (~150ms) dwarfs every other cost by 2-4 orders of magnitude — prioritize batching/caching to reduce the number of cross-region calls first, since even perfect local optimization can't compensate for one unnecessary internet round trip. For the local random-read problem, moving to SSD (~20x faster sequential reads than HDD) and/or restructuring access to be more sequential/batched would be the next highest-leverage fix — but only after the cross-region call count is addressed, since network cost is the dominant term here.

11. Common Mistakes & Misconceptions

  • "Logging is always slow because it's disk I/O." Wrong — logging is sequential write I/O, which is fast; the real risks are unbatched writes and synchronous logging blocking the main thread, not disk I/O itself.
  • "More RAM means we should give the JVM a bigger heap." Wrong — heap size and GC pause time are directly linked; oversized heaps hurt performance even without hitting physical memory limits, because GC sweep cost scales with heap size.
  • "Fewer threads always means less throughput." Wrong — in I/O-bound workloads, a well-designed single-threaded event loop can outperform a naive multi-threaded model by eliminating context-switch overhead.
  • "Denormalize for performance" as a default. Wrong — normalization is the default (saves memory and disk space); denormalization is a targeted fix applied only when load testing proves disk I/O from multi-table joins is the actual bottleneck.
  • "REST is always the right protocol internally." Wrong for high-volume internal traffic where interoperability isn't needed — binary/RPC protocols (gRPC, Thrift) meaningfully reduce data-transfer overhead, at the cost of no longer being "RESTful."
  • "Compression isn't worth the CPU cost." Wrong — compression cost is measured in microseconds while the network transfer it avoids can cost milliseconds to hundreds of milliseconds; the trade is almost always favorable, especially over the internet.
