1. Core Concept & Intuition

One-Sentence Definition

Caching improves performance by serving a request from a nearby, already-computed copy of data instead of re-doing the expensive work (a DB query, a service call, a file read) to produce it again — trading a small risk of staleness for a large reduction in latency and load.

Why This Concept Exists

Every technique in the previous three notes sets (efficiency, network/memory/disk/CPU latency, concurrency) was about doing necessary work faster. Caching is different in kind: it's about avoiding the work entirely when possible. The industry problem: no matter how efficient your database queries or how well-tuned your locks are, a request that never has to reach the database at all will always be faster than one that reaches it efficiently. This is why the instructor calls caching out separately — it requires "minimal code changes" yet produces "phenomenal" performance improvement, precisely because it sidesteps the cost model of everything discussed so far rather than optimizing within it.

Architecture Analogy

Think of a library with a librarian's desk:

  • Without caching, every question — even "what time do you close?" — requires the librarian to walk to the archive room and look it up from scratch.
  • With caching, the librarian keeps a sticky note at the desk with frequently-asked, rarely-changing answers (closing time, today's date) — no archive trip needed.
  • The two risks of this sticky note: (1) the desk only has so much room for sticky notes (limited cache space — you can't cache everything), and (2) if the closing time changes and nobody updates the sticky note, the librarian gives a wrong answer with total confidence (staleness/inconsistency) — this is the central tension the whole topic revolves around.

How a Real System Sees It

In the reference system, caching opportunities exist at every layer, each with a different scope and different data:

  • Database → Service: object cache for data fetched from the DB (not user-specific).
  • Service → Web Application: session cache for user-specific computed/fetched data.
  • Web Application → Browser (static assets): reverse proxy / load balancer cache, and eventually CDN.
  • Browser itself: browser cache for static assets, so repeat visits skip the network entirely.
  • Intranet, client-facing: proxy server (public, shared cache serving multiple users' browsers), separate from reverse proxy (private cache in front of your own web application instances).

2.1 System Architecture Recap — Where Everything Fits (bridges to caching)

Before introducing caching's own architecture, the instructor recaps everything from earlier in Module 1 as context for why caching sits where it does:

  • Web app / network layer: persistent connections, response compression, efficient encoding.
  • Thread pools & DB connection pools: must be used (never create raw threads/connections ad hoc), and sized optimally (covered in Concurrency notes).
  • Concurrency: efficient logging, appropriate use of pessimistic/optimistic locking.
  • Query optimization: called out again as potentially "the biggest source of latency" — requires DB internals knowledge, but has outsized payoff.
  • Async logging, sequential/batch I/O (batching DB updates, appending to logs/files in bulk).
  • Normalization vs. denormalization, revisited: denormalization speeds up requests needing joins; normalization is generally better for write performance (less data to write) and — new point for this lecture — normalization makes data representation more compact, which makes it easier to cache. This is the direct bridge from the schema-design discussion into caching.
  • Indexing, done appropriately.

2.2 What's Newly in Scope for Caching

  • DB buffer cache: exists, but is internally managed by the database itself — acknowledged, not discussed further (out of architect's direct control).
  • Data fetched from DB into services: cacheable.
  • Content caching for static data (unchanging data).
  • Session caching (including caching SSL session parameters at the server — a direct callback to the network-latency notes' "SSL session caching" concept — so the client and server don't have to renegotiate connection parameters repeatedly).

2.3 Caching Architecture — Where Each Cache Sits

Working backend-to-frontend:

Location What's cached Scope Notes
Object cache (service layer) Data fetched from the database Not user-specific — shared across any user Avoids repeated identical DB calls for the same data
Session cache (web application layer) User-specific computed/fetched data Per-user Same underlying mechanism as object cache, just scoped to a user session
Reverse proxy / load balancer (in front of web app) Static content (images, CSS, JS, HTML) Shared, private to the system Can serve static content directly, without ever reaching the web application; disk space here can be substantial (tens of GB)
CDN / public cache Static content, at internet scale Public Flagged for deeper discussion later (Scalability module)
Browser cache Static content Private, per-client Repeat visits skip the network call entirely

Common thread across all cacheable data (static or dynamic): it doesn't change very frequently, and it's accessed frequently enough that caching it pays off. Both conditions are necessary — data that changes constantly, or data that's rarely accessed, isn't a good caching candidate even if the other condition holds.

2.4 HTTP Caching of Static Data

Two intermediary caching points, with a key public/private distinction:

Cache type Location Classification Why
Proxy server Close to the client (e.g., an office's outbound proxy) — many browsers behind it all converge through it Public Any user's data can be cached here, and it's inspectable/shared — e.g., an administrator can view what's cached
Reverse proxy Close to the system — sits in front of (possibly multiple instances of) the web application Private Scoped to the system's own traffic
Browser cache The client itself Private Scoped to that one user

Which requests are cacheable?

  • GET requests (reads) are good caching candidates.
  • POST, PUT, DELETE (all of which modify data) are not candidates for caching.
  • Not every GET is a good candidate — a GET serving frequently-changing data shouldn't be cached even though it's a GET.

How caches know what/how long to cache: the Cache-Control header
Set by the web application (or by the reverse proxy itself, if it directly hosts static content) on the response. It tells every intermediate cache (browser, proxy, reverse proxy) two things: whether to cache, and for how long.

Directive Meaning
no-cache (Slightly misleading name) — the object can be cached, but must be revalidated with the origin server before being used every time.
must-revalidate Similar to no-cache, except validation is only required after max-age has already passed.
no-store Unambiguous — the object must not be cached at all.
public Any intermediate public cache may cache this object — appropriate for data useful to multiple users (not a security directive; purely a caching-scope hint). Contrast: a private/per-user resource (e.g., a profile image) shouldn't be marked public, since a public cache caching it provides no benefit.
max-age How long (client, proxy, or reverse proxy) may cache the object before it's considered expired.

ETag — resource versioning for validation

  • An ETag is a version identifier attached to a resource (e.g., "version 1" for an image).
  • Combined with Cache-Control: no-cache, every time the browser wants to use its cached copy, it must check with the origin first, presenting its cached ETag value.
  • If the ETag matches the current version on the server → browser is told it can keep using its cached copy.
  • If the resource has changed (e.g., updated to "version 2" on the server) → server tells the browser the ETag doesn't match → browser reloads the resource and updates its cache with the new ETag.
  • As long as the ETag stays the same (or max-age hasn't expired), the browser keeps using its cached copy without needing to reload.

🔑 In short: Cache-Control says whether/how long to cache; ETag (with no-cache) provides a cheap way to check whether the cached copy is still valid without re-downloading the entire resource every time.

2.5 Caching of Dynamic Data

Two approaches: exclusive cache and shared cache. Needed at both the service layer (data from DB) and the web application layer (e.g., user profile data).

Exclusive Cache (per-node, in-process memory):

  • Each instance of a service/web app caches data in its own memory.
  • No routing required: any request can go to any instance; if that instance doesn't have the data cached yet, it fetches and caches it locally.
  • Trade-off: since requests aren't routed to a specific node, the same data can end up duplicated across multiple nodes' caches. Once most nodes have "warmed up" (cached the relevant data), effectiveness improves — but duplication itself is an accepted cost.
  • Optional refinement — intelligent routing: use a cookie to remember which node served a given user before, and route that user back to the same node on subsequent requests (a form of session affinity / sticky sessions). This eliminates duplication, at the cost of requiring routing logic (with scalability trade-offs flagged for later discussion).
  • When to use without routing: for small datasets (e.g., a currency conversion table) — cheap to duplicate everywhere.
  • When to use with routing: for large-but-per-user datasets (e.g., user profile / session data across a huge user base) — can't duplicate everywhere, so intelligent routing (session cache pattern) becomes necessary.
  • Performance characteristic: very fast — data is served straight from the instance's own memory, no extra network hop.

Shared Cache (external, centralized component — e.g., Memcached, Redis):

  • Caching responsibility is externalized to a separate component, shared by all nodes.
  • Disadvantage: an extra network hop to reach the external cache (adds some milliseconds).
  • Advantages (in exchange for that hop):
    • No intelligent routing needed — there's only one cache, so any node can query it directly.
    • No data duplication — a single shared copy.
    • Easily scales out — the cache technology itself (Memcached, Redis) handles clustering/scaling, letting it hold much larger datasets than any single node could hold in-process. (Deeper scaling mechanics deferred to the Scalability module.)

🔑 Decision framing: exclusive cache = fast but either duplicated-or-needs-routing; shared cache = one extra hop but simpler (no routing, no duplication) and scales further. Choice depends on dataset size, per-user vs. shared nature of the data, and whether the extra network hop cost is acceptable.

2.6 Caching-Related Challenges

Measuring cache effectiveness: Cache Hit Ratio

Cache Hit Ratio = (Number of Cache Hits) / (Total Number of Requests)
                = (Cache Hits) / (Cache Hits + Cache Misses)

Higher ratio → more requests served from cache → more effective caching strategy. Lower ratio → caching strategy isn't paying off as expected.

Limitation #1: Limited Cache Space

  • Caches are memory-backed, and memory is not cheap — you generally cannot cache everything a database holds (which can be many terabytes, cheaply stored on disk).
  • Decide what to cache using two properties, both required:
    1. Read-only / infrequently-changing data.
    2. Frequently accessed data.
    • Example given: slow-moving inventory items are read-only (rarely change) but rarely accessed → not worth caching. Fast-moving consumer goods are both unchanging and frequently accessed → excellent caching candidates.
  • Prefer caching smaller objects over larger ones, all else equal — caching fewer, larger objects wastes limited cache capacity that could otherwise hold many more smaller, equally-useful objects.

Limitation #2: Cache Invalidation / Staleness
The core problem: data changes at the source (DB) but the cache still holds the old value — the cache becomes inconsistent.

Two mitigation approaches:

  1. Update/delete cache on source write (write-through / write-invalidate style):
    • When the source is updated, also update (or simply delete, forcing a cache miss + repopulation) the corresponding cache entry.
    • Requires: the cache must be owned/controlled by your own system — this approach is impossible for external/public caches (e.g., a public proxy cache from the HTTP caching discussion) that you don't control.
    • Advantage: keeps the inconsistency window extremely narrow (milliseconds — just the gap between the two separate system updates).
  2. TTL-based expiration (used identically in HTTP caching as max-age):
    • Every cached item carries a time-to-live; after it expires, the next request is treated as a cache miss and refetches/repopulates.
    • Advantage: works even for public/external caches you don't control, since the cache itself enforces expiry without needing a "please invalidate this" signal from your system.
    • Disadvantage — the core trade-off:
      • TTL too high → data can be updated at the source far more often than the TTL assumed, leaving the cache stale for a long window (e.g., TTL = 1 hour, but source updates every 5 minutes → up to ~55 minutes of staleness).
      • TTL too low → the cache is refreshed far more often than the underlying data actually changes, hitting the origin unnecessarily and reducing the cache hit ratio — largely defeating the point of caching.
    • No universal correct value — it must be tuned per dataset based on its actual real-world change frequency, and re-adjusted as that frequency changes over time.

3. Deep Technical Explanation

Why caching is categorically different from every prior optimization

Every technique before this (efficient algorithms, connection pooling, batching I/O, minimizing lock duration) reduces the cost per unit of necessary work. Caching instead reduces the amount of necessary work itself by substituting a cheap memory lookup for an expensive recomputation. This is why its ROI is described as disproportionate: you're not shaving milliseconds off a DB query — you're often eliminating the query (and the network hop, and the disk I/O, and the lock contention it might have caused) entirely.

Why the read-only + frequently-accessed criteria are both strictly necessary

Caching cost (memory, invalidation complexity) is paid regardless of whether the data is actually useful once cached. Data that's read-only but rarely accessed pays the cost with almost no benefit (few cache hits). Data that's frequently accessed but changes constantly either can't be safely cached at all, or requires such a short TTL that hit ratio collapses anyway. Only the intersection of both properties yields a cache entry that's both safe (won't mislead many requests with stale data) and valuable (actually gets hit often enough to justify its memory footprint).

Why exclusive cache duplication is an acceptable trade-off for small data but not large data

Duplication cost scales with (data size) × (number of nodes). For a small dataset (currency table), this product stays small regardless of node count — cheap insurance for simplicity (no routing needed). For large, per-user datasets (profile data across millions of users), the same duplication would multiply a already-large dataset by the node count, becoming both memory-prohibitive and largely wasteful (most nodes would cache data for users who never visit them) — hence the need for either intelligent routing (keep exclusive caching, but route to avoid duplication) or a shared cache (eliminate duplication structurally).

Why TTL tuning is fundamentally a statistical guess, not an engineering constant

Unlike max-age/TTL as configured in code, the actual real-world update frequency of the underlying data is not a fixed, known constant — it can change over time (e.g., a marketing campaign suddenly causing more frequent price updates). This means TTL selection is inherently a bet on future data-change behavior, which is why the instructor explicitly frames it as something you "may have to readjust" — it's an empirically-tuned parameter, not a one-time architectural decision.

5. Production System Perspective

  • Netflix / large CDNs: the reverse-proxy-to-CDN-to-browser-cache chain described here is exactly how Netflix serves video thumbnails, UI assets, and static content globally — each layer (browser, CDN edge, origin reverse proxy) is a larger-scope, longer-lived version of the same caching hierarchy in these transcripts.
  • Amazon (product catalog): the "fast-moving vs. slow-moving inventory" caching example maps directly onto real product-catalog caching decisions — high-traffic SKUs (bestsellers) are prime caching candidates, while long-tail rarely-viewed products often aren't cached at all, exactly per the read-only + frequently-accessed rule.
  • Stripe / payment APIs: SSL session caching (mentioned explicitly in the architecture recap) is a real, production technique used to avoid repeated TLS handshake costs on high-volume API traffic between trusted, repeat clients and the API gateway.
  • Discord / session-heavy apps: user session data is a textbook case for either exclusive-cache-with-sticky-routing or a shared Redis-backed session store — the classic trade-off between fast per-node caching (with routing) versus simpler, centralized shared caching, playing out at real scale.

6. System Design Perspective

  • Scalability: shared caches (Memcached/Redis) are explicitly called out as easy to scale out — this is a direct enabler for horizontal scaling of the rest of the system, since it removes per-node memory as a hard ceiling on how much can be cached.
  • Reliability: cache invalidation strategy choice affects blast radius during incidents — a write-through cache tied tightly to your DB writes can itself become a failure point if the cache is unavailable during a write; TTL-based caches degrade more gracefully (worst case: serve slightly stale data) but at the cost of potential staleness windows.
  • Cost optimization: cache space is explicitly framed as an expensive resource compared to disk-backed DB storage — over-caching (or caching poorly-chosen data) is a direct, quantifiable cost, not just a performance consideration.
  • If you ignore this concept entirely: every single request re-executes the full cost chain discussed across the last three notes sets (network round trips, DB disk I/O, lock contention) even for data that's identical to what was served a second ago — an enormous, entirely avoidable tax on system performance and cost.

7. Performance Analysis

  • Cache hit ratio as the central health metric: unlike raw latency/throughput, cache hit ratio directly tells you whether your caching strategy itself (not the underlying system) is working — a system can have great average latency yet a poor cache hit ratio if most traffic happens to hit uncached, unique data.
  • TTL tuning as a latency-vs-freshness dial: shorter TTLs trade cache hit ratio (and therefore average latency) for freshness; longer TTLs trade freshness for hit ratio — this is a direct, quantifiable performance/consistency trade-off, not a one-size-fits-all setting.
  • Shared cache network hop cost: the "extra milliseconds" of a shared cache's network hop must be weighed against the milliseconds saved by avoiding the original DB/service call — for most systems this trade is heavily favorable, but it's not free, and matters more for ultra-low-latency paths.
  • Object size vs. cache capacity trade-off: given fixed cache memory, favoring smaller objects increases the number of distinct items cacheable, directly improving the odds of a cache hit across a more diverse request pattern.

8. Real-World Architecture Examples

1. E-commerce product catalog (static + dynamic mix)

  • Problem: product images/CSS/JS are static (perfect for reverse-proxy/CDN caching); product pricing and inventory counts are dynamic but change at very different rates depending on the product.
  • Why this architecture: static assets get long max-age + ETag-based revalidation; pricing/inventory gets a much shorter TTL or, for high-contention hot items, a write-through invalidation strategy tied directly to inventory updates (echoing the pessimistic-locking-for-hot-items decision from the Concurrency notes).
  • Trade-off accepted: slow-moving catalog items are deliberately not cached, freeing cache capacity for the frequently-accessed, fast-moving subset.
  • Failure scenario: setting one global TTL for all products regardless of individual change frequency would either stale out fast-changing hot items or waste cache capacity refreshing slow-changing ones constantly.

2. User-profile/session data across a large user base

  • Problem: session data is per-user, large in aggregate (millions of users), and needs to be quickly available wherever a given user's request lands.
  • Why this architecture: this is the textbook shared-cache case — a Redis/Memcached-backed session store avoids the impossible alternative (duplicating every user's session across every node).
  • Trade-off accepted: one extra network hop per session lookup, in exchange for avoiding both duplication and the complexity of sticky-session routing infrastructure.
  • Alternative considered: exclusive cache + cookie-based sticky routing — viable, but introduces its own scalability constraints (deferred to the Scalability module) around uneven load distribution when certain users are much more active than others.

3. Public API serving data through an external CDN/public cache the origin team doesn't control

  • Problem: the origin team has no way to explicitly invalidate a public proxy cache sitting between users and their service.
  • Why TTL-based expiration is the only viable strategy here: the write-through/invalidate-on-write approach fundamentally requires ownership of the cache — impossible for a public intermediary.
  • Trade-off accepted: some window of potential staleness is unavoidable, bounded only by how conservatively (or aggressively) max-age/TTL is set.
  • Failure scenario: setting max-age too long on frequently-updated public data leads to widespread stale responses across many independent public caches, with no way to force-invalidate them — a real operational risk unique to caches outside your control.

10. Interview Questions

Basic

  1. What two properties should data have to be a good caching candidate?
    → It should be read-only/infrequently-changing, and frequently accessed. Both are required — data missing either property is a poor caching candidate (rarely accessed data wastes cache space even if stable; frequently-changing data risks serving stale results even if popular).
  2. What's the difference between a public cache and a private cache in the context of HTTP caching?
    → A public cache (e.g., a proxy server) can store and serve cached responses for any user, and is generally shared/inspectable. A private cache (browser cache, reverse proxy) is scoped to a single user or a single system's own traffic.
  3. Why are GET requests generally cacheable while POST, PUT, and DELETE are not?
    → GET requests are reads that don't modify server state, making a cached copy safe to reuse. POST/PUT/DELETE modify data, so caching their result (or reusing a cached response in their place) would break correctness.

Intermediate

  1. When would you use an exclusive (per-node) cache versus a shared (external) cache?
    → Exclusive cache suits small datasets that are cheap to duplicate across every node (e.g., a currency table) or larger per-user datasets combined with intelligent/sticky routing. Shared cache (Memcached/Redis) suits large, shared datasets where duplication is wasteful and you want to avoid routing complexity — at the cost of one extra network hop per access.
  2. Explain how ETag and Cache-Control: no-cache work together, and why this differs from simply setting a long max-age.
    → no-cache forces the browser to revalidate with the origin on every use of a cached resource, sending its stored ETag. The origin compares this to the resource's current ETag — if they match, the cached copy is reused (cheap validation, no re-download); if they don't, the browser re-downloads the updated resource. This differs from a long max-age alone, which would let the browser use its cached copy without any check for the full duration — risking staleness if the underlying resource changes before expiry.
  3. What are the two main strategies for handling cache staleness, and when would you use each?
    → (1) Update/delete the cache entry whenever the source is updated (write-through/invalidate-on-write) — narrow staleness window, but only works for caches your own system controls. (2) TTL-based expiration — works even for external/public caches you don't control, but requires tuning a duration that balances staleness risk (TTL too high) against wasted cache hits (TTL too low).

Advanced

  1. A team sets a single, long max-age/TTL for all product data in their catalog cache to maximize cache hit ratio. During a flash sale, prices and inventory update every few minutes, but customers report seeing stale prices for up to an hour. Diagnose the issue and propose a fix.
    → The single long TTL was tuned for the catalog's typical (slow) update frequency, but the flash sale dramatically increased the actual update frequency without a corresponding TTL adjustment — a direct instance of the "TTL too high relative to actual change rate" failure mode. Fix: use a shorter, dynamically-adjustable TTL for actively-promoted/flash-sale items specifically (rather than one global TTL for the whole catalog), or switch those specific hot items to a write-through invalidation strategy (assuming the cache is owned by the team) so price/inventory changes propagate to the cache immediately rather than waiting out a fixed TTL.
  2. Your system uses exclusive, per-node caching without routing for user session data, and you're seeing high memory usage per node along with a surprisingly low effective cache hit ratio despite heavy overall traffic. Explain why, and describe two different fixes with different trade-offs.
    → Without routing, any user's session can land on any node, so every node ends up independently caching a broad, largely non-overlapping slice of the full user base — this is the duplication problem scaled up to a dataset far too large for that to be cheap (unlike the small currency-table example). Each node wastes memory on entries it will rarely re-serve (since the same user may not return to that node), which also depresses the effective hit ratio per node. Fix 1: introduce intelligent/sticky routing (cookie-based, routing a user consistently back to the node that cached their session) — keeps the fast in-process cache but adds routing infrastructure and complexity. Fix 2: switch to a shared external cache (Redis/Memcached) — eliminates duplication and routing entirely, at the cost of one extra network hop per session lookup, and gains easier horizontal scalability of the cache itself.
  3. A public CDN caches your API's responses, and you need to push out a data correction immediately, but you don't operate the CDN. Walk through why your usual cache-invalidation approach won't work here, and what you'd need to rely on instead.
    → The write-through/invalidate-on-write approach requires direct control over the cache so you can push an update or deletion the moment the source changes — a public CDN you don't operate offers no such hook. You're structurally limited to whatever TTL/max-age was set when the response was originally cached; the correction won't reliably reach all cached copies until each one's TTL naturally expires. In practice, this means the only lever available ahead of time is having set a sufficiently conservative (short) max-age on data that might need urgent correction — after the fact, you may also be able to invoke provider-specific purge/invalidation APIs if the CDN offers one, but that's outside the general HTTP caching mechanism described here and depends entirely on the specific CDN's tooling.

11. Common Mistakes & Misconceptions

  • "Caching always improves performance." Wrong — caching data that's rarely accessed, or data that changes too frequently to safely serve stale, wastes limited cache capacity or introduces correctness risk with little to no benefit.
  • "Cache-Control: no-cache means the response won't be cached." Wrong — despite the name, it means the response can be cached but must be revalidated with the origin before each use. no-store is the directive that actually prevents caching.
  • "A longer TTL is always safer / better." Wrong — a longer TTL increases the window during which a cache can serve stale data if the source updates more often than expected; it's a trade-off, not a one-directional safety improvement.
  • "A shorter TTL is always safer." Also wrong in the opposite direction — an excessively short TTL causes unnecessary re-fetches even when the underlying data hasn't changed, tanking cache hit ratio and largely defeating the purpose of caching.
  • "Exclusive (per-node) caching is always faster and therefore always preferable." Wrong — it's faster per-access, but for large, per-user datasets without routing, it leads to heavy duplication and doesn't scale the way a shared cache does.
  • "Public cache directives (public) are a security mechanism." Wrong — public is purely a caching-scope hint (this data is safe/useful to share across users), not an access-control or security setting.
  • "You should always favor caching the largest, most expensive-to-compute objects first." Wrong per the transcript's explicit guidance — given limited cache space, smaller objects should generally be favored, since they let you cache more distinct items overall, improving aggregate hit ratio.

latency: network/memory/disk/CPU) → concurrency (queuing + coherence, locking, deadlocks) → caching

caches discussed here reappear as first-class scaling tools (e.g., Memcached/Redis clustering, CDN edge
caching, load-balancer-fronted reverse proxies) once the discussion moves from a single machine to many.
